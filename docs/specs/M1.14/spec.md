## M1.14a — request protection (done)
- **CSP builder** (`@yayatoh/platform/security`, pure, runs in `proxy.ts`):
  - *Strict* profile for console, checkout, sign-in, token pages (tickets, orders, claims, invitations) and the scanner: a fresh 128-bit nonce per response + `'strict-dynamic'` (+ `'self'` fallback). `frame-ancestors 'none'`.
  - *Public* profile for the home page, event pages, legal and privacy pages: a host allowlist (`'self'` and named https origins that must be loaded with `integrity`, i.e. SRI) without `'strict-dynamic'`, plus the nonce while the pages render per request. `frame-ancestors 'self'`.
  - Both: `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `style-src 'self' 'nonce-…'`, **`style-src-attr 'none'`**, `report-uri` + `report-to`. Never `'unsafe-inline'` or `'unsafe-eval'` for scripts in production (`'unsafe-eval'` only under `next dev`; the scanner adds `'wasm-unsafe-eval'` for its WebAssembly decoder). Extra sources are validated (keywords and wildcards are refused).
  - Every page renders per request (`connection()` in the root layout) so it carries its nonce.
- **Other headers** per page type: HSTS (2 years, includeSubDomains) on https; `X-Frame-Options`; `Referrer-Policy` (`no-referrer` on secret-link pages, `same-origin` in the console, `strict-origin-when-cross-origin` on public pages); `Permissions-Policy` (camera only on `/scan`); COOP and CORP `same-origin`; `nosniff`. API routes get `default-src 'none'; frame-ancestors 'none'`.
- **Fixes the CSP needed** (no loosening): Zod's JIT probe (`new Function`) is disabled in the browser (`instrumentation-client.ts`, `z.config({ jitless: true })`); SSR style attributes were removed (Avatar and chart sizes are classes; brand colours are applied through the CSSOM after hydration). 404s for dotted paths now pass the proxy too.
- **CSP report endpoint** `POST /api/csp-report`: `application/csp-report` and `application/reports+json`, 16 KB cap, rate-limited, logs directive/blocked/document without query strings (tokens never reach logs).
- **`serverActions.allowedOrigins`** from `SERVER_ACTIONS_ALLOWED_ORIGINS` (empty by default, `*` refused).
- **Rate limiter** (`@yayatoh/platform/security`): sliding-window counter (two-bucket approximation) with exact Retry-After; stores: memory, **Postgres** (`platform.rate_limits`, UNLOGGED, only through the SECURITY DEFINER `platform.rate_limit_hit`; matches the TS algorithm hit for hit) and **Upstash Redis REST** (Lua script; used when `UPSTASH_REDIS_REST_*` is set). Policies count per device cookie (`yy_did`, set by `proxy.ts`, HttpOnly) or per IP without one, per identity (email, SHA-256 hashed) and a generous per-IP ceiling — venue Wi-Fi shares one IP, so tight limits are per device. Fails open if the store is down (logged).
- **Applied to:** password and code sign-in, emailed sign-in codes (in front of Better Auth, whose own per-IP sign-in rule is switched off for those paths), checkout start, the holder magic link and passing a ticket on, forged webhooks (only failed signature checks count; signed deliveries are never limited). Dev login is not limited (it does not exist in production). 429 + `Retry-After` + `RateLimit-*` headers; localized "Try again in N minutes" in sign-in, checkout and holder-link forms (13 locales, Arabic plurals). **The M1.7e seat finder should adopt `limitRequest`/`limitAction` at merge; M1.2c should add its 2FA verify paths to the auth route's list.**
- **SSRF guard** (`@yayatoh/platform/ssrf`): https only (http opt-in), no credentials, ports 443/80, blocked hostnames (`localhost`, `.local`, `.internal`, …), every resolved address must be public unicast (IPv4 private/loopback/link-local/CGNAT/multicast/doc/benchmark ranges; IPv6 loopback, unspecified, ULA, link-local, site-local, multicast, documentation, NAT64, 6to4, Teredo/2001::/23, IPv4-mapped/compatible), `safeFetch` pins the socket to the checked address (DNS rebinding), follows at most 3 redirects re-checking each hop, drops credentials across origins, and caps time and size.
- `robots.txt` keeps crawlers out of the console and secret-link pages.

## M1.14b — org-facing audit view (done)
- **Hash chain** on `platform.audit_events` (migration): per-org `seq` (gap-free, per-org advisory lock), `prev_hash`, `hash = sha256(jsonb[prev, org, seq, actor, action, target, data, request, created_at µs])`, set by a BEFORE INSERT trigger; existing rows back-filled; CHECK added `NOT VALID` then validated. app_user still can't update or delete.
- `verifyAuditChainTx` recomputes every hash in SQL and checks links and numbering: edits, deletions and re-hashing are detected (truncating the newest entries needs an external anchor of the head — owner inbox, WORM).
- **`platform.auditLog` query** (`audit:read`: owners and admins): filters by person, action, and date range (org-timezone days), keyset paging by `seq`, filter options, chain status. **Allowlisted output:** the raw `data` is never returned; only scalar details under known keys (no emails, names or free text).
- **CSV export** through the bulk framework (`platform.auditCsv`, 2 000-row chunks, 50 000 cap, injection-safe, org timezone, actor display names passed from the member list); the export itself is audited.
- **Settings → Activity** (`/o/{org}/activity`, nav item and a link from Settings for owners/admins): "Verified · N entries, hash chain intact" or an alert naming the first broken entry; filters in the URL (survive reload); date validation messages; empty states; older/newest paging; export with progress and download (`/activity/exports/{op}`, re-checks the permission). Other roles get a refusal on the URL and no nav item.

## M1.14c — privacy (done)
- **New module `@yayatoh/privacy`** (tier 5, schema `privacy`, table `dsar_requests`: kind, SHA-256 subject ref, masked hint, requester, per-category counts; never the address). Per-module read/erase helpers added to crm, attendees, ticketing, orders, forms, checkin, events and platform (modules still never touch each other's schema).
- **Find a person** (`privacy.findSubject`, `privacy:manage`: owners and admins): counts across contacts, consents, orders (paid), tickets (valid), claim links, holder links, guest-list entries, checkout answers, check-ins, plus earlier requests.
- **Access request**: `privacy.dsarExport` bulk action → one JSON file (`yayatoh.dsar/1`): contacts, consents, orders with items and refunds, tickets, claims, holder links, attendee records, form answers (sensitive answers decrypted, with question labels), check-ins, event names. Allowlisted: no tokens, hashes, provider ids, fee schedules, signing material or internal contact ids. The email in the operation's params is cleared a day after it finishes; the file expires in 7 days.
- **Erasure** (`privacy.eraseSubject`): the email must be typed again. One tenant transaction redacts in place: contacts (unique placeholder), orders (name, email, account link, payment reference, manage-link ciphertext; refund notes), tickets (holder; `updated_at` moves so doors resync), claim links (addresses; open ones revoked), holder links (deleted), attendees (name, email, labels), staged import rows (deleted), form answers (cleared). **Legal holds:** paid orders, ledger postings, consent rows and admissions are kept (without personal data). Export files that mention the address are deleted. Audited without the address.
- **Retention** (`privacy.retention`, system actor, daily per org in the worker, idempotent, audited with counts): expired export files; finished bulk-operation params (30 days; privacy exports 1 day); idempotency keys; never-paid checkouts lose buyer details and answers after 30 days; holder links 30 days after expiry; unclaimed claim links lose the address 90 days after expiry; scan log after 12 months (admissions stay); attendee and ticket-holder PII 24 months after the event. Globally: expired rate-limit counters; the platform access log after 12 months **only** with `ACCESS_LOG_ARCHIVED=1` (SECURITY DEFINER refuses anything younger than 12 months). Defaults pending owner.
- **Console:** Settings → Privacy requests (`/o/{org}/privacy`): find (emails travel in POST bodies only), results by category, export with download, erase with an explanation of what is kept and a typed confirmation, and the history of requests (masked).
- **Public pages:** `/privacy` (Yayatoh privacy notice) and `/sub-processors` (list, purposes, data, locations, 30-day notice) — drafts marked for counsel, in 13 locales; linked from the home page and the console.

## M1.14e — DSAR for Yayatoh's own accounts, team invitations, erased-address suppression (done)
Yayatoh is the **controller** for accounts (identity, sessions, security history, which orgs a person works in); each org stays the controller of its own customers (orders, tickets, contacts, consents).

- **Self-service (account page, `/account/security`):**
  - *Download my data:* "Confirm it's you" (step-up, 10 minutes), then `GET /api/account/export` returns `yayatoh.account/1` JSON: profile, sign-in methods (booleans, never hashes), sessions (device, IP, times; never tokens), security events (action + allowlisted `method`/`purpose`/`by`), memberships and roles, notification choices and click-wrap acceptances per org, their orders and tickets per organizer (the fields the buyer already sees), marketing consents, team invitations. Allowlisted by a Zod document schema (unknown keys dropped). Recorded in `privacy.account_requests` (masked) and as a security event `account.exported`. Signed out → 401; stale step-up → 403.
  - *Delete my account:* the email typed again + step-up. Refused (`invalid_state`, reason `last_owner`) while the person is the only owner of any org; the page then hides the form and names the orgs, and a stale form submitted later gets the same message. On confirm: the confirmation email goes to the old address first (dev mailbox in dev/CI; platform sender, 13 locales, no unsubscribe), then **per org** a platform command (`privacy.detachAccount`, `platform:` permission → system actor only) removes the membership (same per-org owner lock as role changes), event roles, notification choices, push tokens and inbox, unlinks orders and contacts from the account and deletes/redacts invitations addressed to them — audited in each org's chain as `privacy.account_erased` against the user id (now pseudonymous; no address in the data). Then the identity is anonymised in one transaction (packages/auth): `account.deleted` security event, every session revoked, credentials, two-step verification and pending codes deleted, email → `sha256(email)+<id>@erased.invalid`, name/picture/language cleared, `deleted_at` set. The address joins the erased list, signup-code notes that mention it are redacted, and the request is recorded. The person lands on `/account/deleted`; their password no longer works; signing in with an emailed code creates a new, empty account.
  - **Orders stay** (legal/accounting hold): the buyer email on an order is the organizer's customer record and stays with the org (they can erase it with their own DSAR tool; the confirmation page says so). Pending owner/counsel.
- **Staff console (`apps/admin`, `/people`, English only):** admin and support staff (`privacy` action; finance has no need to see or erase personal data — pending owner). Find by email across accounts (live and earlier deleted ones, by hash), staff role, memberships, team invitations (all orgs), orders as a buyer, signup codes (created or mentioning the address), sessions, security events, the erased list and earlier requests — one audited platform_reader read whose access-log reason carries a masked address only. Export (same document) and erase (same rules, no step-up for the subject) each need a written reason (10–500 characters), recorded with `staff:<id>` in `privacy.account_requests`; erase also needs the email typed again and is refused for active staff (revoke with the owner CLI first). An address without an account can be erased too (its invitations).
- **Team invitations in the org-side DSAR (M1.14c gap):** `privacy.findSubject` counts invitations, the access export lists `teamInvitations` (email, role, status, dates; never the inviter), and erasure deletes open invitations and redacts the address on accepted/revoked ones.
- **Platform-wide erased-address suppression:** `platform.erased_addresses` (SHA-256 of the NFC-normalized, trimmed, lower-cased address; reason `erased`; `created_at`; `account_lifted_at`; never the address). Global, no app_user privileges; SECURITY DEFINER `erased_address_add` / `_lookup` / `_lift_account`. Written by org-side erasure and account deletion (a repeat erasure restarts the clock).
  - *Dispatcher (every org):* **order mail** (transactional kinds about an order or ticket: tickets, refunds, claim and holder links, seat-finder codes, replies the customer asked for) still goes out — it exists only for an order being fulfilled or a new one; **account mail** (team invitations, member notifications) goes out once the person has signed up again; **org mail** (reminders, event updates, marketing) is suppressed (`reason: erased`, shown in the order's message log) until that org records a new marketing consent captured after the erasure. Pending counsel.
  - *Guest-list import (every org):* an erased address is skipped at "Check rows" and at import time with the reason "This person's data was erased at their request" (in the counts and the "rows that can't be imported" CSV).
  - *Signup:* allowed. A new account for the address lifts the suppression for account mail only (Better Auth `databaseHooks.user.create.after` → `liftErasedAccountMail`); org marketing needs a new consent.
- **Retention of the anonymised rows (pending owner):** the anonymised `auth.users` row and its `security_events` are kept while any org audit entry, order or record names the id (at most the 7-year accounting hold of the orders they bought), then may be deleted by a later retention job; `privacy.account_requests` and `platform.erased_addresses` are kept for 7 years (accountability / proof of erasure; hashes only). The message log keeps delivery rows (evidence); `recipient_email` on queued org messages is not yet redacted (see Later).
