# Spec: M7.5a — Store launch kit

- **Milestone:** M7.5a (Phase 7 plan `docs/plans/mobile.md`, decisions P7-4, P7-7, P7-8, P7-9, P7-10; brief `docs/agent-briefs/m7.5a.md`). Built 2026-10-15, branch `agent/m7.5a`.
- **Status:** Built. Files, scripts and the runbook; **no store, EAS, Apple, Google or Sentry account was touched**. The owner runs the first submission (`docs/runbooks/mobile-release.md` §1).
- **Risk tags:** `legal-copy` (store text, privacy labels, compliance answers, reviewer notes), `auth` (a fixed email code for one address, non-production only), `infra` (EAS profiles, a new tooling package)
- **Related ADRs:** 0002, 0010, 0011, 0025

## 1. Goal
Everything the stores ask for, written down, checked by tests and runnable from one runbook: listings in 13 locales for both apps, screenshots (a plan and the flows that capture them), privacy labels derived from the shipped libraries, export-compliance and age-rating answers, the App Review notes, a reviewer demo, EAS build, update and submit profiles, and the release runbook.

## 2. What was built

| Area | What it is | Files |
|---|---|---|
| **Listings** | Apple (EAS Metadata format, `configVersion 0`) and Google Play listings for Yayatoh and Yayatoh Staff in the 13 locales: title, subtitle, keywords, description, promotional text, short description, release notes, categories, age-rating `advisory`, phased release on and automatic release off, and the review contact and notes. URLs, contact details and the demo values are `${NAME}` placeholders filled from the environment. English first; the 12 others are translated. | `apps/<app>/store/store.config.json`, `play.json` |
| **Store kit** | A tooling package that checks and renders those files: limits per store and locale (title 30, subtitle 30, promo 170, description 4000, keywords 100, Play short 80, notes), no untranslated copy, no literal URLs, `render` (fills placeholders, names any value that is missing, refuses non-https URLs), `privacy`, `compliance`, `screenshots`, `shots` and `check` commands. App scripts: `store:check`, `store:render`, `privacy:check`. | `tools/store-kit/` |
| **Privacy labels** | App Store privacy labels and Play Data safety as data: each data type (Apple and Play names, linked to the user, optional, purposes, who collects it), each shipped dependency reviewed with what it collects, each permission mapped to its data types. `privacy:check` walks the app's `dependencies` and those of the workspace packages it uses, and its production Expo config's permissions, and fails on: a dependency not reviewed, a reviewed one that is gone, a known collector (Sentry, notifications, location) missing its data type, an analytics-looking name with nothing collected, a label via a library that is gone, a permission added or dropped, tracking turned on. | `apps/<app>/store/privacy.json`, `tools/store-kit/src/privacy.ts` |
| **Compliance** | Export compliance (standard algorithms only; `ITSAppUsesNonExemptEncryption = true`, written into the iOS build by `buildExpoConfig`, with an optional `IOS_ENCRYPTION_COMPLIANCE_CODE`), the age-rating answers for Apple and Google (IARC), and the App Review guideline answers: no in-app purchase because tickets are physical services (3.1.3(e)), virtual and livestream access is not sold in the app, account deletion in Account (5.1.1(v)), Sign in with Apple beside Google (4.8), minimum functionality (4.2), privacy (5.1.2), and how a reviewer uses Staff. The check ties the review notes to the guidelines the answers rely on and the export answer to the app config. | `apps/<app>/store/compliance.json`, `packages/mobile-core/src/app-config.ts` |
| **Screenshot plan** | Six screens per app, three required device sets (iPhone 6.9″, iPad 13″, Android phone) plus optional ones, light and dark, English first; one Maestro flow per screen that signs in with the reviewer demo and takes a numbered screenshot; a capture script that sets appearance and the status bar and runs the flows; the output folder layout; `shots` checks every PNG exists at its device's exact size. | `apps/<app>/store/screenshots.json`, `apps/<app>/.maestro/store/*.yaml`, `tools/store-kit/capture.sh`, `apps/<app>/store/capture.sh` |
| **Reviewer demo** | `pnpm reviewer-demo --target=local\|staging`: the demo organization `app-review-demo`, a running event "App Review Concert" (began yesterday, ends in 180 days, so the door is always open), a paid and a free ticket type, a marketplace listing so Discover finds it, the reviewer attendee's ticket (bought by email, so it appears at first sign-in), three unscanned door tickets, and the Staff door device with its enrolment link (shown once; `--rotate-door` replaces it). Idempotent. Refuses production by environment name (`YAYATOH_ENV`, `VERCEL_ENV`, `NODE_ENV`), by database host (local hosts, or `REVIEWER_DEMO_HOSTS` for `--target=staging`) and by payment provider (fake only); the guard runs before any other module loads. | `apps/web/scripts/reviewer-demo.ts`, `reviewer-demo-guard.ts`, `reviewer-demo-run.ts` |
| **Fixed email code** | `createAuth` takes `fixedEmailCodes`; `reviewerFixedCodes(env)` builds it from `REVIEWER_DEMO_EMAIL` and `REVIEWER_DEMO_CODE` (six digits). Returns nothing in production, and `createAuth` ignores the option in production as well. Only that address; every other address keeps a random code. Wired in `apps/web` and `apps/api`. | `packages/auth/src/auth.ts`, `apps/web/src/server/auth.ts`, `apps/api/src/auth.ts` |
| **EAS** | Build profiles `development`, `preview`, `production` (each with its channel, EAS environment name and `APP_ENV`; `production` is a store build with an automatic build number). Submit profiles `testflight`, `play-internal`, `play-closed` and `production` (Play staged rollout at 5%, iOS metadata path). The runtime version stays `fingerprint`. No account value anywhere in either file. | `apps/<app>/eas.json` |
| **Runbook** | Build, submit to the test tracks, closed testing, store metadata and screenshots, review and phased release, staged rollout, over-the-air fixes and when not to use them, the 72-hour event freeze, minimum-version bumps (never for Staff inside an event window), rollback, rejections, and the owner's first-submission checklist. | `docs/runbooks/mobile-release.md` |

**What was chosen** (all in `docs/owner-inbox.md`, "M7.5a"): review runs against a review server because the fixed code cannot exist in production; export compliance is "uses standard encryption" (`true`), not "exempt"; Yayatoh rated 12+ and Staff 4+; EAS options that could not be checked offline are marked UNVERIFIED in the runbook.

## 3. Not yet / later
- **Everything that needs an account or a device:** the first submission, App Store Connect and Play Console forms, uploading screenshots and the Play listing, TestFlight and Play testing, the review server, real values for the `STORE_*` names. The runbook lists them in order.
- **Screenshot images.** The plan, flows and capture script exist and are checked; the PNGs come from the device pass. Non-English captures are a second pass.
- **Native-speaker review** of the 12 translated listings, and counsel's review of the privacy policy text, export classification and rating answers.
- **Staff push** is not enabled in the app config yet (M7.4c's note), so Staff's Android notification permission is not declared; the label for its push token is already in `privacy.json`.
- The Staff reviewer demo has no exhibitor or organizer account.
