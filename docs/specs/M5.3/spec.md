# M5.3 — Speaker portal and CFP

## M5.3a — speaker portal (done)

Phase 5 plan (`docs/plans/phase-5.md`, approved 2026-09-29), Wave 1; decisions P5-1 (build now behind the `speakers` module key), P5-7 (portal accounts), P5-10 (scope), P5-11 (free in beta). Roadmap M5.3, §4.1–4.2. Risk tags: `auth`, `tenancy`, `db-migration`, `legal-copy`.

**Built**
- **Portal accounts (P5-7), the shared foundation for all four portal roles** (`@yayatoh/events`: `domain/portal-auth.ts`, `portal.ts`, `schema-portal.ts`). A portal account is one event role (`speaker`, `exhibitor_admin`, `exhibitor_staff`, `sponsor_contact`) at one event for one program row (`subject_kind`, `subject_id`). It is **not** an org member and not a Better Auth user: inviting creates an `events.event_role_assignments` row whose `user_id` is the account id, expiring with the event + 90 days. No console, no TOTP.
  - **Invitations** are signed links `/event-portal/invite/{org}~{account}~{version}~{hmac}` (APP_TOKEN_SECRET). The tenant comes from the signed token, never a header. Re-inviting the same address bumps the version (older links say "a newer invitation was sent"); revoking ends the account, its assignment, sessions and pending codes at once; after the event + 90 days everything says "this portal has closed". Emailed by the outbox (`portal.account_invited@1` → `events.portal-invite-mailer`, kind `portal.invite`, transactional); events carry no token.
  - **Sign-in** follows the M1.5f guest rules exactly: the invitation page emails a 6-digit code **and** a magic link (kind `portal.sign-in`, sent at once, never queued); codes 10 minutes, single use, 5 wrong tries lock it (even against the right code), 30 s between codes, a new code retires the old; the link works once, for 15 minutes, only in the browser that asked (`yy_gs` state); opened elsewhere it spends nothing and asks for the code from the same email. Rate limits through the M1.14 limiter (`guestCode` / `guestVerify` policies, `portal` scope: per device, per address, per IP).
  - **Sessions:** cookie `yy_portal` (`__Host-` on HTTPS), host-only, httpOnly, value `{org}~{secret}`; the row stores only the secret's HMAC; 7 days, never past the account's expiry. Sign out revokes the row.
  - **`requirePortalPrincipal()`** (`apps/web/src/server/portal.ts`) returns `{ orgId, eventId, eventRoleAssignmentId, role, subjectId, subjectKind, accountId, email, expiresAt }` (M5.4a codes against the first five). Commands run with a new kernel actor `{ type: 'portal', accountId, role }` (audit actor `portal:{account}`); the tenancy authorizer allows it **only** `portal:{its role}` permissions and refuses everything a member can do (and members never get `portal:*`). Every portal command re-reads the account in its transaction (`portalPrincipalTx`: live, not revoked, event + 90 days, assignment still granted, same role) and checks the subject.
- **Speaker portal** (`/event-portal`, strict CSP, noindex): overview (their event with dates and **times in the event's time zone**, their sessions with room, track and co-speakers, open tasks), profile, one page per own session, tasks. Any other session id — another speaker's, another event's, a guess — is a 404; the console redirects to sign-in.
- **Proposed changes the organizer approves** (`program.speaker_changes`): profile (name, title, company, bio, links, photo) and session (title, description) changes are stored with the approved values they started from (`base`); one pending proposal per speaker and target (a new one supersedes). **Proposed changes** page (`/o/{org}/e/{event}/speakers/changes`) shows each as a current → proposed diff with the proposed photo, approve / reject with an optional note (shown to the speaker), audited with the fields (`program.speaker_change.approve|reject`). Approval writes only the changed fields, re-sanitized, and is refused (`stale`) when the organizer edited one of them since, so it never silently overwrites an edit. The public agenda reads only the approved rows. An approved photo becomes the speaker photo through media (`program.speaker_change.decided@1` → `media.speaker-photo-approver`, re-encoded like an organizer upload; the web applies it at once, the worker is the backstop).
- **Tasks**, generic by subject kind (`speaker` now; M5.4 adds `exhibitor`): `program.portal_tasks` (kind `upload`, `agreement` or `confirm`, title, instructions, agreement text, due date) and `program.portal_task_assignees` (status per assignee). Creating a task assigns every speaker of the event ("Add N new speakers" later). Speakers answer in the portal: a file (`upload`), accepting the agreement text (`agreement`, the speaker release: placeholder wording, `legal-copy`) or a tick (`confirm`). **Files go through media** (`media.portal_files`): bytes sniffed (PDF, PowerPoint .pptx, Word .docx, JPEG, PNG, WebP; photos: images only, decodable, ≤ 4 MB), ≤ 25 MB, stored as uploaded under `{org}/{file}/f-{hash}.{ext}`, never public; organizers (and viewers) download them from the board (`/api/portal-files/{org}/{file}`, `events:read`).
- **Organizer task board** (`/o/{org}/e/{event}/speakers/tasks`): tasks with due dates (event time zone), each speaker's status, completion time, file and reminders, and "Remind N speakers missing X".
- **Reminders "to whoever is missing X"** (`program.remindMissing`): exactly the assignees who have not completed the task, through each live portal account of theirs (invited or signed in; one message per address), via the notifications dispatcher (kind `program.task-reminder`, transactional, policy gate, fake providers). The answer says how many were emailed and how many have no access. **Scheduled pre-due reminders** are planned on today's reminder planner (`sendAfter` 48 h before the due date, at once when closer; dedupe key per assignee, account and due date) when a task is assigned or a speaker invited; completing or deleting a task cancels them.
- **Outbox events** for the future M5.9a alert rules (no alert engine is called): `program.speaker_task.completed@1` (once: completing twice is refused) and `program.speaker_task.overdue@1` (once per assignee: `overdue_at` records it; the worker sweeps every minute through the SECURITY DEFINER `program.orgs_with_overdue_tasks`). Payload: task, assignee, event, subject kind and id, due date.
- **Gate:** every organizer and portal command needs the `speakers` module (P5-1); organizer writes need `events:write` (viewers read everything, change nothing, and a stale form is refused).
- **Messages:** `speakerPortal`, `portalSignIn`, `speakerAccess`, `speakerChanges`, `speakerTasks` and three notification-kind labels in all 13 locales (valid plurals, Arabic RTL); email templates `portal.invite`, `portal.sign-in`, `program.task-reminder` and the four portal role names in all 13 locales.

**Migration** `0076_long_luminals.sql` (to be renumbered at merge; expect to regenerate it with M5.2a's program changes): `events.portal_accounts`, `events.portal_challenges`, `events.portal_sessions`, `program.speaker_changes`, `program.portal_tasks`, `program.portal_task_assignees`, `media.portal_files` (all tenant tables, RLS forced, org-leading indexes, composite FKs). Hand-written (between `-- hand-written: begin/end`): the composite FKs from `program.portal_tasks`, `program.portal_task_assignees` and `program.speaker_changes` to `events.events` (cascade); `program.orgs_with_overdue_tasks(timestamptz, int)` SECURITY DEFINER (org ids only), granted to `platform_reader` only; `REVOKE ALL` on `events.portal_challenges` and `events.portal_sessions` from `platform_reader`.

**Choices pending owner** (owner inbox): the portal invitation stays valid until the event + 90 days (reissue or revoke to end a link sooner); 7-day portal sessions; pre-due reminder 48 h before; overdue sweep every minute; files ≤ 25 MB of PDF/PPTX/DOCX/JPEG/PNG/WebP; the speaker release wording (placeholder, `legal-copy`).

## M5.3b — call for papers (done)

Phase 5 plan (`docs/plans/phase-5.md`, approved 2026-09-29), Wave 2, row M5.3B; decisions P5-1 (the `speakers` module), P5-7 (portal accounts), P5-11 (free in beta). Builds on M5.3a (portal sign-in), M1.4f/M5.2a (program, agenda) and the forms engine. Risk tags: `auth` (a new portal role), `tenancy`, `db-migration`, `legal-copy` (CFP wording).

**Built**
- **The call** (`program.cfp_calls`, one per event): not open yet (hidden) / open / closed, an optional deadline entered in the event's time zone, the session lengths speakers can ask for (15–90 min presets), co-speakers allowed (0–5), blind review, and an introduction. Settings page `/o/{org}/e/{event}/speakers/cfp/settings`; opening with a deadline already past is refused.
- **Extra questions through the forms engine**: a new form kind `cfp` (subject the event; checkout field types; nothing sensitive) with add/remove commands; every change is a new immutable version, so answers keep theirs. The generic `forms.publishForm` refuses the `cfp` kind (the `speakers` gate stays in program).
- **The public form** `/events/{slug}/cfp` (phone first, 44 px targets, noindex; a draft call is a 404, a closed one says so): title, abstract, length, track, name, email, job title, company, bio, up to N co-speakers (optional rows), the extra questions. The org and event come from the event's public page (`pageTarget`), never a header; the M1.14 limiter policy `cfpSubmit` (device, address, IP). Every error marks and focuses its field and keeps what was typed; a duplicate (same address and title) is refused; success replaces the form with a confirmation and emails `program.cfp-received`.
- **Reviewers** (`program.cfp_reviewers`) are **portal accounts** with the new event role `cfp_reviewer` (P5-7: invited by email, code or magic link, no console, ends with the event + 90 days); re-adding an address re-invites; "End access" revokes. Organizers assign reviewers per proposal (`cfp_assignments`).
- **Reviewers see only assigned proposals:** the reviewer portal (`/event-portal` for a reviewer, `/event-portal/reviews/{id}`) lists and opens only the reviewer's own assignments; anything else (another reviewer's, another event's, a guess) is a 404 and the commands answer `not_found`. **Blind review** hides names, job titles, companies, bios, co-speakers and the extra answers (the queries never read them). Score 1–5 as large radio pills (arrow keys) and a comment for the organizers (`cfp_reviews`, one per assignment), editable until decided.
- **Organizer pages** `/speakers/cfp` (submissions with review count and mean score), `/speakers/cfp/reviewers`, `/speakers/cfp/{id}` (abstract, speakers, answers, reviews with names, assign/remove, decide): design-v2 `PageHeader`, `Tabs`, `StatusPill`, `Table`, `EmptyState`, `Alert`. Viewers read everything and see no control; a stale form is refused.
- **Decisions with emails:** accept or decline with an optional note; decided once (row lock; a double click or a second organizer gets "already decided"); every speaker on the proposal is emailed `program.cfp-accepted` or `program.cfp-rejected` in the submitter's language with the note (outbox `program.cfp_submission.decided@1` → `program.cfp-mailer`, transactional, fake providers in dev/CI).
- **Accepting creates the speaker and exactly one draft session:** speakers matched by email in the event (`speaker_contacts`; reused, never duplicated) or created with the submitted profile; one session (`program.sessions.draft = true`, placeholder at the event start for the requested length, the requested track, all speakers linked). `cfp_submissions.session_id` is unique. Drafts are excluded from the public agenda, its published snapshot, `/v1` and schedule warnings, and a speaker whose only sessions are drafts is not on the public speaker list. The sessions page shows a Draft badge and "Add “…” to the agenda".
- **Messages:** `cfp`, `cfpPublic`, `cfpReview`, `speakerPortal.roles.cfp_reviewer`, three `notifications.kinds.program.*` labels (13 locales, Arabic RTL, no plural forms needed); email templates `program.cfp-received`, `program.cfp-accepted`, `program.cfp-rejected` and the role `cfp_reviewer` in all 13 locales.

**Migration** `0103_abandoned_spot.sql` (to be renumbered at merge): `program.cfp_calls`, `cfp_submissions`, `cfp_co_speakers`, `cfp_reviewers`, `cfp_assignments`, `cfp_reviews` (tenant tables, RLS forced, org-leading indexes, composite FKs, org-scoped uniques); `program.sessions.draft boolean not null default false`. Hand-written (between `-- hand-written: begin/end`): the five changed CHECKs on existing tables re-added `NOT VALID` then `VALIDATE` (`events.event_role_assignments_role_check`, `events.portal_accounts_role_check`, `events.portal_accounts_subject_kind_check`, `forms.forms_kind_check`, `forms.form_responses_respondent_type_check`); composite FKs from `cfp_calls`, `cfp_submissions`, `cfp_reviewers`, `cfp_assignments` to `events.events` (cascade); `cfp_submissions` → `program.speakers` and → `program.sessions` with `ON DELETE SET NULL (speaker_id)` / `(session_id)` (deleting the session or speaker keeps the decision).

**Choices pending owner** (owner inbox, M5.3b): reviewers as portal accounts; what blind review hides; accept creates speakers + one draft session (no automatic portal invitation); decisions final; limits and the `cfpSubmit` rate limit; CFP terms wording (`legal-copy`).

**Later / not yet**
- A link to the call from the public event page and the tenant site (`/t/{org}/…`); today the organizer shares `/events/{slug}/cfp` ("Open the public form").
- Reopening a decided proposal; bulk assignment ("assign every reviewer to every proposal"); reviewer conflicts of interest; reviewer reminders; score rubrics or several criteria; exporting proposals.
- A per-question "show to blind reviewers" switch; CFP terms / consent checkbox (`legal-copy`); attachments (slides, video) on proposals.
- A reviewer-specific line in the shared portal invitation email.
- M5.2b enrollment should refuse draft sessions (they are `included` by default and not public, so nothing reaches registrants today).
