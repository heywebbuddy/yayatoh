# Spec: M7.4c — Door tools

- **Milestone:** M7.4c (Phase 7 plan `docs/plans/mobile.md`, decision P7-6)
- **Status:** Built (2026-10-14). App code only (`apps/staff`), plus two additive lines in `packages/mobile-core` and `apps/staff/src/scan/engine.ts` (see §2). Stacks on M7.4a (device session, portal session, organizer sign-in) and M7.4b (saved manifest, offline scanner).
- **Risk tags:** `mobile-contract` (calls `/v1/staff/*`, `/v1/portal/leads/*`, `/v1/orgs/{org}/events/{event}/ops`; adds no route)
- **Related ADRs:** 0002, 0010, 0011, 0014, 0025

## 1. Goal and users
Door staff on an enrolled device, exhibitor reps and organizers get the day-of tools of the Scan PWA in the Staff app: find a guest and check them in by hand, check in from the guest list, work the help-request queue, see today's numbers and alerts (and get them as pushes), capture leads with the badge scanner (offline too), and, for organizers, a read-only event-day view that refreshes while open.

## 2. What was built
Screens live in `apps/staff/src/tools/screens/*` and are mounted by thin routes under `src/app/tools/`. Every screen reads its collaborators from one `ToolsDeps` context (`tools/deps.tsx`), which `tools/runtime.tsx` builds from the device session, the saved manifest and offline scanner, the portal session and the account session. Tests give the screens fakes.

| Route | Screen | Calls |
|---|---|---|
| `/tools` | hub: shows only what this phone may do (door tools for an enrolled device, leads for a signed-in rep, event day for a signed-in organizer) | none |
| `/tools/lookup` | find by name, phone or email; manual check-in with a required reason | saved manifest (offline), or `GET /v1/events/{event}/manifest` pages held in memory; `POST /v1/checkins` |
| `/tools/guests` | guest list search by name, party, label; check-in; outbox | `GET /v1/staff/events/{event}/guests`, `POST /v1/staff/guest-arrivals` |
| `/tools/assistance` | open queue; take, start, resolve, cancel; ask for backup | `GET /v1/staff/events/{event}/assistance`, `POST /v1/staff/assistance[/{id}/{action}]` |
| `/tools/today` | checked in against expected, by entrance and day, devices, alerts; staff push toggle | `GET /v1/staff/events/{event}/overview`, `GET/PUT/DELETE /v1/staff/push` |
| `/tools/leads`, `/leads/scan`, `/leads/[id]` | licence and window, leads, badge capture, rating, qualifiers, notes, outbox | `GET /v1/portal/leads/setup`, `GET /v1/portal/leads`, `POST /v1/portal/leads/scans`, `PATCH /v1/portal/leads/{id}` |
| `/tools/ops` | organizer picks organization and event, then read-only ops view (refreshes every 15 s while the app is in the foreground) | `GET /v1/me/organizations`, `GET /v1/orgs/{org}/events`, `GET /v1/orgs/{org}/events/{event}/ops` |

**Lookup.** One matching function, `findTicketHolders` from `@yayatoh/checkin-engine` (the Scan PWA's and the console's), runs over the manifest rows: the saved manifest of M7.4b when there is one (works offline; email and phone match by exact salted hash), otherwise rows downloaded through the device's manifest route and kept in memory only. A match is copied field by field into five fields (name, pass type, short code, status, admitted-here); hashes and every other manifest field never reach a screen.

**Manual check-in.** A reason is required (a note is required for "another reason"). Online it is `POST /v1/checkins` by short code with one idempotency key per attempt; offline, or when the server cannot be reached, it is the scanner's own offline verdict (`engine.scan`), which queues the scan in M7.4b's outbox. An answer from the server (even a refusal) is final and never falls back.

**Guest list.** The last guest snapshot is kept in the encrypted tools vault for offline use. Check-ins go into an encrypted outbox (one `clientId` each), are sent in batches of up to 500 and are flagged when the server says someone checked the guest in earlier.

**Leads.** Scans go into an encrypted outbox before anything is sent (batches of up to 200, each `scanId` once); edits to a queued scan ride along with it. The outbox is owned by the rep's address, so another rep on the same phone never sees or sends it. Lead fields are reduced to `sharedFields` (P5-8); an email shows only with consent and not withdrawn. The rep's licence, the lead terms and the capture window (P5-4) gate scanning, and the server decides again for every scan. Query keys carry a session key that changes at every sign-out, and the lead queries are removed from memory then.

**Staff push.** The toggle asks for permission, takes the APNs or FCM token from `expo-notifications` (behind a port with a fake) and registers it with the notification text in the phone's language. The text is the app's own words with the server's `{label}` and `{percent}` placeholders: no personal data.

**Storage.** `tools/vault.ts` seals JSON files (XChaCha20-Poly1305, the cache's seal) under a key of its own in secure storage. Remote wipe, revoke and removal delete the key and the files (`ToolsWipe`, registered in the root layout through M7.4a's `onWipe`).

**Small edits outside `apps/staff/src/tools`:** `packages/mobile-core/src/index.ts` exports `seal`, `openSealed`, `toBase64`, `fromBase64`; `apps/staff/src/scan/engine.ts` gets a `lookupSource` getter (rows, salt, admitted today); the root layout mounts `<ToolsWipe />`; `expo-notifications` joins the catalog and the Staff app.

## 3. Not yet / later
- **Server gaps (no route was added):** (1) there is no device-token lookup route, so online lookup downloads manifest pages into memory (the same rows the device already holds); (2) `POST /v1/checkins` has no `reason` field, so the manual-check-in reason is kept in the phone's encrypted audit log (short code, reason, result; no name) and not sent; (3) `/v1/staff/events/{event}/overview` has no realtime transport in the app, so numbers poll every 15 s.
- **Push needs one line when M7.3d merges:** set `staff.push: true` in `packages/mobile-core/src/app-config.ts` (M7.3d adds the flag) so the `expo-notifications` config plugin and `POST_NOTIFICATIONS` apply to Staff; add the FCM file secret for Staff.
- The guest-saving card QR shown after a guest arrives (M4.8e) is not shown.
- Unsent leads stay encrypted on the phone after a rep signs out, until that rep signs in again or the device is wiped.
- An organizer's alert rules without a translation show a generic line.
