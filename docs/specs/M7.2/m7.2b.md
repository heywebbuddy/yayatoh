# Spec: M7.2b — My tickets API

- **Milestone:** M7.2b (Phase 7 plan `docs/plans/mobile.md`, decision P7-5)
- **Status:** Built (2026-10-14). Server only: no app code, no real Apple or Google wallet call. Stacks on M7.2a's `/v1/me` scope.
- **Risk tags:** `tenancy`, `mobile-contract` (owner approval needed before main). No migration.
- **Related ADRs:** 0002 (one command model), 0010 (auth), 0011 (QR and offline check-in), 0014 (allowlists)

## 1. Goal and users
The attendee app shows a signed-in person their tickets, their orders, and lets them pass a ticket on, ask for a refund, add a ticket to a wallet and claim a ticket someone sent them. A person is their session's **verified email address**, exactly as on the web's My tickets: a ticket or order is theirs only if that address bought it or holds it. Everything goes through the web's queries and commands; this adds no new way to read across organizations.

## 2. What was built
All routes sit under M7.2a's `/me` scope (a user bearer session with a verified email; an API key is 401, an unverified account 403 `email_unverified`). `/claims/*` mounts the same guard. Nothing takes an email or an org from the request: the address is the session's, and the org is found from it.

**Reading across orgs.** The orgs where the address holds a ticket or bought an order come from the lookup that already exists for native push, `notifications.app_orgs_by_email` (SECURITY DEFINER, ids only, shipped in M7.2c). Each org is then read in its own tenant transaction under its RLS (`withTenant`), up to six at a time. The order list is `guestOrders(email, null)` itself (the web's source, through `orders.order_refs_by_email`); order detail and the refund credential use the same `order_refs_by_email`. **No SECURITY DEFINER function was added.** A ticket or order id is only ever looked up inside the orgs the address already belongs to, so another person's id, an id in an org the person has nothing in, and an id that does not exist are the same 404.

| Route | What it does |
|---|---|
| `GET /v1/me/tickets?when=upcoming\|past&limit&cursor` | The active tickets held by the address, across organizers: event summary (instants + time zone), type, seat, `rev`, short code, organizer name and accent colour, whether a transfer is pending. Upcoming soonest first, past latest first; opaque keyset cursor; `ETag` + `If-None-Match` → 304. No QR codes in the list. |
| `GET /v1/me/tickets/{id}` | The QR code string (the current signed `yy1` payload; null once voided), short code, `rev`, status, type, seat, the entrances and zones where the type is checked, the event, the venue (saved venue's address, map link and accessibility notes, else null), the organizer's branding (name, absolute logo URL, event-or-organizer accent colour, "powered by"), and the transfer options (allowed, reason, deadline, fee, fee-requires-web, pending transfer and its recipient's name). |
| `GET /v1/me/orders`, `GET /v1/me/orders/{id}` | Orders bought by the address (paid, partially refunded, refunded), newest first; detail has lines, subtotal/discount/fee/total in minor units, the refund policy the order was bought under, the refund-request panel (latest request, may-request-now, refusal, deadline), the tickets still held and how many were passed on. |
| `POST /v1/me/orders/{id}/refund-requests` | `requestRefundCommand`. The manage-link token the command wants is decrypted from the order's own envelope on the server and never leaves it. The policy, one-open-request and ticket checks are the command's. 201. |
| `POST /v1/me/tickets/{id}/transfers` | Starts a transfer by name and email: `ticketing.startAppTransfer`, which runs `startTransferTx`, the same core as `startHolderTransferCommand` (`transfersAllowed`, `transferCutoffHours`, same-holder, void/ended, one pending transfer per ticket). 201 `started`. A ticket type with a **transfer fee** is not started: 200 `web_payment_required` with `webUrl` (`{web}/my-tickets/{holder link}`) where the fee is agreed and paid. |
| `DELETE /v1/me/tickets/{id}/transfers/{transferId}` | `ticketing.cancelAppTransfer` (only the holder, only the transfer of that ticket). 204. |
| `GET /v1/me/tickets/{id}/wallet?platform=apple\|google` | A pass link from `WalletPassProvider.passLink` (the fake: `https://wallet.fake.yayatoh.test/{platform}/{serial}`, until the owner's Apple and Google accounts exist). One live pass per ticket and code revision, made on first use. Only an active ticket the person holds. |
| `GET /v1/claims/{token}`, `POST /v1/claims/{token}` | What a claim or transfer link offers (state, event, type, organizer, sender/recipient names of a transfer; no code), and `ticketing.claimTicketForPerson` with the session's verified address (a transfer can only be claimed with the address it was sent to). The POST returns the claimed ticket (same shape as the detail). |

**Shared cores, no duplicated rules.** `startHolderTransferCommand`/`cancelHolderTransferCommand` were not changed. The app commands are siblings over the same `startTransferTx`/`cancelTransferTx`, differing only in how the holder is proved: the session's verified address instead of a holder link (a link would have to be created per request and would make idempotent retries unstable). `claimTicketCommand`'s body moved to `claimTicketTx`, shared with `claimTicketForPersonCommand`; the web's output is unchanged. `claimTicketForPerson` mints no holder link, so no web credential is stored in an idempotency record.

**Responses and writes.** Every response is an allowlist (`toWire` over a declared schema; the module DTOs are also `defineSerializer`s). Money is minor units; instants are ISO strings with the event's zone beside them. Every write requires an `Idempotency-Key` (kernel step 5; the same key replays the stored answer, a different body is 422). The one exception is the transfer-fee branch, which only issues a holder link (rate limited three an hour per event and address by the existing rule) and is deliberately not stored in an idempotency record because its answer is a web credential. The sender's transfer response and the claim response never carry the claim token or the holder token.

**Wallet and transfers.** Claiming a transfer reissues the ticket (`rev` + 1: the old code is `superseded` at the door, online and offline), rotates the wallet pass (the old pass `voided`, a new one for the new holder and revision) and the existing `ticketing.wallet-pass-sync` subscriber tells the provider (void old, issue new). `WalletPassProvider` gained `passLink`.

**Contract.** `apps/api/openapi.json` and `packages/sdk/src/schema.ts` regenerated; additions only (`oasdiff`), Spectral clean. New operations: `listMyTickets`, `getMyTicket`, `startMyTicketTransfer`, `cancelMyTicketTransfer`, `getMyTicketWalletPass`, `listMyOrders`, `getMyOrder`, `requestMyOrderRefund`, `getTicketClaim`, `claimTicket`. New response enums are complete: `MyTicketStatus`, `TransferRefusal`, `WalletPlatform`, `TicketCheckpointKind`, `RefundPolicyKind`, `RefundRequestStatus`, `RefundRefusal`, `ClaimState`, `TransferOutcome`, `TicketWhen`.

## 3. Module changes (public exports only)
- `events`: `eventTicketFactsTx` (an event's venue id and accent colour).
- `checkin`: `checkpointsForTicketTx` (live entrances and the zones a type may enter; names and kinds only).
- `ticketing`: `myTicketsTx`/`MyTicketDto`, `startAppTransferCommand`, `cancelAppTransferCommand`, `claimTicketForPersonCommand`, `issueAppHolderLinkCommand`, `holderWalletPassTx`, `markWalletPassesPushedTx`, `WalletPassProvider.passLink`, `WALLET_PLATFORMS`.
- `orders`: `myOrderDetail`, `myOrderRefundTarget`, `MyOrderDetailDto`.
- `api-v1`: `routes/me.ts`, `me/service.ts`, `me/resources.ts`; `V1Deps.walletPasses` (default: the fake provider).

## 4. Not yet / Later
- Pages are cut from the person's whole ticket set on each request (a person holds a handful across a few orgs; a hard bound of 500 per org and 500 orgs). A materialized per-person index is a later change if it is ever slow.
- A ticket the person holds but whose org has no active ticket or sold order for the address any more (everything voided) is found only by a direct detail read where the org still counts via an order; a fully voided history is not listed.
- Transfer fees are paid on the web; in-app payment is a later change. The recipient's claim link reaches them by email (the existing `transferMailer`); deep linking into the app is M7.3.
- The wallet link is a placeholder until the Apple Pass Type ID and Google Wallet issuer exist (`docs/owner-inbox.md`). Pass contents/signing are the real providers' job.
- Order detail shows no invoice, credit notes or message log (the web's order page does); add as the app needs them.
- Device pass: the wallet add flows on a phone; the QR rendering and brightness; deep links from emails.
