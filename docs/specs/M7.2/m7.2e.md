# Spec: M7.2e — Staff API

- **Milestone:** M7.2e (Phase 7 plan `docs/plans/mobile.md`, decision P7-6)
- **Status:** Built (2026-10-13). Server only: no app code. Stacks on M7.2a (`/v1/me` scope, app sign-in) and M7.2c (APNs and FCM transports).
- **Risk tags:** `auth` (a bearer form of the exhibitor portal session, device-token routes), `mobile-contract` (21 new `/v1` operations), `db-migration`
- **Related ADRs:** 0002 (one command model), 0010 (auth), 0011 (QR and offline check-in), 0014 (allowlists)

## 1. Goal and users
The Staff app (door staff, organizers, exhibitor reps) needs everything the Scan PWA gets from `/api/scan/*`, plus the exhibitor portal's lead retrieval and an organizer's event-day view, over `/v1`. The PWA and the app must never drift, so each read and write lives in one function that both call.

## 2. What was built
**One implementation (`packages/api-v1/src/staff/*`, exported as `@yayatoh/api-v1/staff`).** The PWA's route handlers (`apps/web/src/app/api/scan/{staff,guests,assistance,assistance/[id],push}`) now call these functions; their URLs, bodies, answers and status codes are unchanged:
`staffOverviewFor` (counts, device board, alerts, realtime channel names), `guestSnapshotFor` and `recordGuestArrivals`, `openAssistanceQueue`, `raiseStaffRequest`, `workStaffRequest`, `staffPushStatus`, `subscribeWebPush`, `registerNativePush`, `unsubscribeStaffPush`, `deviceFromAuthorization` (the device token to its org context), `checkinCardEntry` (moved from `apps/web/src/server/saved-card.ts`, re-exported there), `alertsEngineWidget` (moved from `apps/web/src/server/command-center.ts`), and `opsViewFor`.

**Device-token routes (`/v1/staff/*`, scheme `deviceToken`).**

| Route | Same as the PWA's |
|---|---|
| `GET /staff/events/{eventId}/overview` | `GET /api/scan/staff` |
| `GET /staff/events/{eventId}/guests`, `POST /staff/guest-arrivals` | `GET`/`POST /api/scan/guests` |
| `GET /staff/events/{eventId}/assistance`, `POST /staff/assistance`, `POST /staff/assistance/{requestId}/{take\|start\|resolve\|cancel}` | `/api/scan/assistance` |
| `GET`/`PUT`/`DELETE /staff/push` | `/api/scan/push` (web push there; APNs and FCM here) |

The token decides the org (never a header or parameter). An unknown, malformed or revoked token is a `401` with `application/problem+json` on every route. A **wiped** device (a supervisor asked it to wipe; its token still resolves so the next heartbeat can deliver `wipe`) is also `401` here, so it gets nothing but the heartbeat. API keys and user sessions are `401` on these routes. The PWA's routes keep accepting a wiped device exactly as before.

**Device push.** `PUT /staff/push` registers `apns` or `fcm` on the device's one `checkin.staff_push_subscriptions` row (a new registration replaces the old one, a browser's too; the supervisor who claimed the alerts is kept when the token is the same). `setDeviceStateCommand` (revoke and wipe) deletes the row, whatever its platform. The alert sender (`sendStaffAlertPushes`) now passes the row's platform, no keys and no URL for native tokens, and `liveTransports` (M7.2c) routes them to APNs or FCM; without live providers they land in the dev mailbox. The token is never returned by `GET /staff/push` and never written to the audit log.

**Exhibitor reps (`/v1/portal/*`, scheme `portalSession`).**
- Sign-in: `POST /portal/auth/code` (invitation token in; the six-digit code is emailed, 10 minutes, five tries; 30-second cooldown), `POST /portal/auth/token` (`grantType` `code` or `refresh_token`), `POST /portal/auth/revoke`, `POST /portal/auth/invitations` ("email me my invitation again", `204` whether or not the address has access). They call the same `requestPortalChallenge`, `verifyPortalChallenge` and `resendPortalInvitations` as the browser, with the M1.14 limiter (`guestCode`, `guestVerify`; Upstash or Postgres counters), and the same refusal for a forged, reissued, revoked or expired invitation (`403`).
- The session (`packages/modules/events/src/portal-bearer.ts`): `yyp_{org}~{secret}` access token (15 minutes) and rotating `yyr_{org}~{secret}` refresh token, in the shape of M1.2f. A spent refresh token presented again ends the session. The session ends at the earlier of a week and the account's expiry (event end + 90 days). **Every request re-reads the account and its event-role assignment**, so revoking either ends the session at once. Only HMACs are stored.
- Lead routes (the M5.6b commands, unchanged): `GET /portal/leads/setup` (licence, terms, capture window, qualifiers), `GET /portal/leads`, `POST /portal/leads/scans` (one scan or the offline queue, up to `SYNC_BATCH_MAX`, applied once per `scanId`), `PATCH /portal/leads/{leadId}` (rating, qualifiers, notes). A rep sees only their own exhibitor's leads (or the team's when the admin shares them); a lead carries only the fields the attendee agreed to share (P5-8); a rep without a licence (P5-4) gets `403`.

**Organizer event-day view.** `GET /v1/orgs/{org}/events/{eventId}/ops` (bearer user session) returns the five door widgets of the web Command Center, loaded by the same widget queries (`executeQuery` of each widget's loader): `checkins` (against expected, per entrance and date), `throughput` (scans per minute, a per-minute series, per entrance and device, queue minutes), `scanIssues` (duplicates, refused, the latest), `devices`, `alerts`, plus `mode`. A section the member's role or plan does not include is `null`. An API key gets `403` ("The Command Center is for members"); a member of another org gets `404`.

**Contract.** `apps/api/openapi.json` and `packages/sdk/src/schema.ts` regenerated; tags `staff` and `portal`; `bearer` schemes `deviceToken` and `portalSession`. The change to `/v1` is additions only (the three changed existing definitions in the file come from M7.2a).

## 3. Migration (`0173_staff_api_sessions.sql`, to be renumbered at merge)
Generated, then edited: `checkin.staff_push_subscriptions` gets `platform` (`webpush`, `apns`, `fcm`; default `webpush`) and `app_id`, and `p256dh` and `auth_secret` become nullable; `events.portal_sessions` gets `kind` (`cookie`, `bearer`), `refresh_hash`, `previous_refresh_hash`, `refresh_expires_at` and a partial unique index on `(org_id, refresh_hash)`. No new table, so no `createOrgFixture` change.
Hand edits (inside `-- hand-written: begin/end`): the new CHECKs are added `NOT VALID` and then `VALIDATE`d (the generated file had them valid); the three old web-push CHECKs on the table (`p256dh`, `auth`, `endpoint`) are dropped and replaced by `platform`-aware `keys` and `endpoint` CHECKs. `private-columns` classifies the new columns (`refresh_hash`, `previous_refresh_hash` secret; `app_id` internal; `platform`, `kind` vocab).

## 4. Not yet / Later
- Organizer sign-in with TOTP for the ops view is M7.2a's `two_factor` grant on `/v1/auth/token`; this increment adds no second check of its own.
- The ops view is a snapshot (pull); the app follows the realtime channels the overview names for live updates.
- Native staff pushes have run against the dev mailbox and M7.2c's recorded provider responses only; real APNs and FCM delivery to a door phone is the device pass.
- A lead export, terms acceptance and licence assignment for reps stay on the web portal.
