# Spec: M7.2c — Native push

- **Milestone:** M7.2c (Phase 7 plan `docs/plans/mobile.md`, decision P7-8)
- **Status:** Built (2026-10-13). Server only: no app code, no real APNs or FCM call. Stacks on M7.2a's `/v1/me` scope.
- **Risk tags:** `infra` (new providers: APNs and FCM), `db-migration`, `legal-copy` (lock-screen wording), `mobile-contract`
- **Related ADRs:** 0002 (one command model), 0014 (allowlists)

## 1. Goal and users
Attendees with the Yayatoh app on a phone get a lock-screen push about their orders, tickets and events: order confirmed, ticket received, transfer accepted or cancelled, event changed or cancelled, and reminders 24 h and 2 h before the start. The text is the event name and what changed, nothing else. A phone only ever hears from an organization where its owner has an order or a ticket.

## 2. What was built
**Providers (infra).**
- `providers/apns.ts`: APNs over HTTP/2 with a `.p8` token (ES256 provider token kept 50 minutes, one refresh on `ExpiredProviderToken`). The topic is the bundle id (the device's own id when it is one of `APNS_BUNDLE_ID`, else the first). The host is chosen per token: `sandbox` or `production`, as the app reported it. Collapse id from the ticket's collapse id; priority 10 for urgent, 5 otherwise.
- `providers/fcm.ts`: FCM HTTP v1 with a service account (RS256 assertion exchanged for a one-hour access token, one refresh on a 401). `collapse_key` and the notification `tag` carry the collapse id; the same id goes in `apns-collapse-id` for iOS devices on FCM.
- Both sit behind `PushTransport`. `nativePushTransport` routes per platform through `routedPushTransport`, and `liveTransports` uses it when `providerMode('apns' | 'fcm')` is `live` (`PUSH_PROVIDER=apns,fcm` plus each provider's names). With nothing live, dev and CI use the dev mailbox exactly as before. Names are in `.env.example`.
- Provider answers: APNs 410 `Unregistered`, 400 `BadDeviceToken` / `DeviceTokenNotForTopic` and FCM `UNREGISTERED` / `SENDER_ID_MISMATCH` / a token-field `INVALID_ARGUMENT` mark the token **expired**: `disabled_at` is set in the org that sent, and in every other org the phone is stored in (`notifications.app_token_disable`). A re-registration clears it. 429 and 5xx retry through the dispatcher's existing backoff (`Retry-After` honoured, capped at an hour); other refusals fail that one message.

**Devices.**
- `push_tokens` gains `app_id`, `app_version`, `locale`, `environment` (with CHECKs). `POST /v1/me/devices` (platform, token, appId, appVersion, locale, timeZone, environment) and `DELETE /v1/me/devices/{token}` sit behind M7.2a's `/me` scope (verified email), keyed by `email_norm`, `source = 'app'`, like `registerOrderPushCommand`.
- Registration stores the phone in each org where the signed-in email has a paid order or an active ticket (`notifications.app_orgs_by_email`), through the command pipeline per org (`notifications.registerAppDevice`, audited without the email). A person with no purchase stores nothing (`organizations: 0`); the app registers again after the first purchase. A phone handed to someone else is released from the previous owner in every org (`app_device_release`). At most 10 phones per person per org (the least recently seen is replaced).
- The orders subscriber `orders.app-push` (in the worker and web registries) copies the person's phones to an org on their first order or transferred ticket there, and queues the reminders of tickets held before the phone was registered. `DELETE` and `purgeAppDevices` remove the rows in every org (`app_device_remove`, `app_devices_purge`).

**Notification types (P7-8)** — eight push-only kinds, `push.*`, templates in 13 locales:

| Kind | When | Opens | Category |
|---|---|---|---|
| `push.order-confirmed` | `order.paid` | `/orders/{id}` | transactional |
| `push.ticket-received` | `ticket.transferred` (recipient) | `/tickets/{id}` | transactional |
| `push.transfer-accepted` | `ticket.transferred` (sender) | `/orders/{id}` | transactional |
| `push.transfer-cancelled` | `ticket.transfer_cancelled` (the party who did not cancel) | `/tickets/{id}` or `/events/{slug}` | transactional |
| `push.event-changed` | `event.updated` with a changed start, end, zone or venue; `event.rescheduled`; `event.postponed` | `/events/{slug}` | transactional |
| `push.event-cancelled` | `event.cancelled` | `/events/{slug}` | transactional |
| `push.reminder-24h` | 24 h before: the same wall-clock time the day before, in the event's zone | `/tickets/{id}` | reminders |
| `push.reminder-2h` | 2 h before: two elapsed hours | `/tickets/{id}` | reminders |

- Reminders: one message per kind, ticket and holder (dedupe `app-{kind}:{ticket}:{email}`), queued when the order is paid, when a ticket is transferred (the sender's are cancelled), or when a phone is registered. They follow reschedules (`rescheduleRemindersTx` now plans each kind from the event as it is) and are cancelled for a cancelled or postponed event, a voided or refunded ticket, and a transferred ticket. A reminder that quiet hours would hold past the event's start is dropped (`suppressed`, `quiet_hours`).
- Preferences: the `reminders` category follows the existing per-org unsubscribe and member preference machinery (`suppressions`, `preferences`); service notices are transactional. `push.*` kinds go to app phones only (APNs, FCM), never to a browser's web push, and the notifier queues nothing for a person without an app phone in that org.
- Lock screen: title is the event name; body is one fixed line per kind (reminders add the start's time of day in the event's zone). The tap payload is `path` (and `lang`).
- `event.updated` now carries `schedule`, the list of `startsAt`/`endsAt`/`timezone`/`venueName`/`venueId` that actually changed (additive payload), so a save that changes nothing sends nothing.
- `/v1` additive: `registerDevice`, `removeDevice` in `apps/api/openapi.json` and `packages/sdk/src/schema.ts`.

## 3. Migration (`0172_previous_vision.sql`, to be renumbered at merge)
Generated: `push_tokens.app_id/app_version/locale/environment` and their CHECKs (added `NOT VALID`, then validated), index `tickets_holder_email_lower_idx` on `lower(holder_email)`. Hand-written (`-- hand-written: begin/end`): six SECURITY DEFINER functions in `notifications` (owner migrator, `search_path = pg_catalog`, `EXECUTE` revoked from PUBLIC and granted to `app_user`): `app_orgs_by_email`, `app_devices_by_email`, `app_device_release`, `app_device_remove`, `app_devices_purge`, `app_token_disable`. Each works on the signed-in person's own address (or a token the provider reported dead) and returns ids or counts, never personal data of anyone else.

## 4. Not yet / Later
- Staff alert pushes are unchanged (M3.4a); marketing pushes stay off (they need a consent-ledger opt-in, M7.3d's settings).
- Reminders go to the holder's address at the time the order is paid; naming a different holder later does not move them (the nominee's own phone is reached once they hold the ticket through a transfer).
- A phone registered before the person has any purchase is not stored (the app registers again after the first purchase). A per-person, org-less pending device table is a possible later change.
- Provider health (the staff page) does not count push sends yet.
- Translations were written by the build; a native-speaker pass is in `docs/owner-inbox.md`.
- Device pass: real APNs and FCM delivery, the tap opening the screen (M7.3d), and the sandbox/production host per build.
