# Spec: M7.3c — Discover and buy (attendee app)

- **Milestone:** M7.3c (Phase 7 plan `docs/plans/mobile.md`, decision P7-7)
- **Status:** Built (2026-10-14). App only (`apps/mobile`, plus two small additive edits in `packages/mobile-core`). No server code, no migration. Fake payment provider throughout: `PAYMENTS_PROVIDER` was never set and no Stripe call was made.
- **Risk tags:** `payments` (the app side of checkout; the server side is M7.2f)
- **Related:** M7.2f (browse and checkout API), M7.2b (orders API), decisions P7-7 (payments in the app) and P7-9 (links), App Review 3.1.3(e)

## 1. Goal and users
A person finds an event in the attendee app, chooses tickets under the web's rules, pays on the provider's hosted page in a secure browser session that returns to the app, and lands on an order confirmation whose tickets are in My tickets. Whatever the app cannot sell natively (live-stream access, carts that need the web) is explained and sent to the web, never sold in the app.

## 2. What was built
**Routes** (`apps/mobile/src/app/`): `(tabs)/discover.tsx`, `events/[slug].tsx`, `e/[code].tsx`, `checkout/[slug].tsx`, `orders/index.tsx`, `orders/[id].tsx`, `orders/link/[token].tsx`, and a stand-in `(tabs)/_layout.tsx` (M7.3a's tab shell replaces it at merge). Screens live in `src/discover`, `src/events`, `src/checkout`, `src/orders`; shared logic in `src/shop`. Strings: namespaces `discover`, `checkout`, `orders` in all 13 catalogs.

- **Discover:** search by words (debounced), category, date range (today, this weekend, next 7 days, this month, or typed `YYYY-MM-DD` dates with a message per mistake), and "near me". Soonest first; nearest first with a position. Keyset paging from the API's `nextCursor` (on reaching the end, or a "Show more" button), pull to refresh, loading, empty, no-connection and rate-limit states. The location is requested **only when "Near me" is tapped**, while the app is open, at coarse precision; the position sent is rounded to two decimals (about a kilometre). A refusal explains itself and, when the system will not ask again, opens Settings. Permission strings: `NSLocationWhenInUseUsageDescription`; Android `ACCESS_COARSE_LOCATION` only (fine and background location are blocked), via `expo-location`.
- **Event page** (`/events/[slug]`, `/e/[code]`): name, organizer, when in the **event's time zone** with the zone shown, venue and "Open in Maps" (the venue's own link, else coordinates, else address; https only), about text as plain words (organizer Markdown is stripped, never rendered), status banners (cancelled, postponed, ended), date picker for multi-date events (cancelled dates hidden, sold-out dates not choosable), passes with all-in prices, early-bird price, "few left", access dates and availability. Organizer branding goes through `BrandScope` (readable colours only); see "Not yet". `/e/[code]` follows the web's short-link redirect to find the slug.
- **Ticket selection with the web's rules** (`shop/selection.ts`): only `available` passes can be chosen; a quantity is 0 or from the pass minimum (packs) to its per-order maximum; sold out, not yet on sale and sales ended say so; promo code at checkout; the cart total is the all-in total, and the server's price is final. The cart (per event) lives for the app process, so it survives the payment page and a cancel link.
- **Checkout** (`checkout/use-checkout.ts`): `POST /v1/public/events/{slug}/checkout` with an `Idempotency-Key` that stays the same for the same cart (quantities, date, promo code) and changes when the cart does. `pay` opens the payment URL in an auth session (`expo-web-browser`) that ends at the event's return link; `paid` goes straight to the confirmation; `web` explains the reason (questions, seats, registration, transfer fee, choose-your-amount) and opens the web checkout, holding nothing. After **any** end of the browser session the order is read from the server before anything is claimed (`/v1/me/orders` shows an order only once it is paid, so an unpaid one answers 404): paid goes to the confirmation, a normal return that the provider has not confirmed yet goes to the order screen as "confirming" (it keeps asking for two minutes), a cancel or a closed sheet returns to the checkout with the selection intact and "Pay again" replays the same key (one order, never two). One checkout per event runs at a time across screens.
- **Return and cancel links:** `?checkout=return|cancelled&order={id}` on `/events/{slug}`. `mobile-core`'s `routeForLink` now keeps those two query fields (and only those, validated) so a universal link lands on the event screen with them; the event screen dismisses the browser session and settles the order.
- **Virtual and livestream tickets (P7-7):** an online event shows "Buy on the web" in place of every stepper; on a hybrid event the 409 `buy_on_web` answer marks the named passes web-only (the rest of the cart stays) and offers the web page. A web-only pass in the cart disables Pay. The server refuses them too (M7.2f); the app never lets the request be sent.
- **Orders** (`/orders`, `/orders/[id]`): the list (status in words, tickets, total in the order's currency, keyset paging, empty state to Discover), and the detail: lines, subtotal/discount/fees/total, dates, passed-on tickets, the refund policy it was bought under and where a refund request stands. After a purchase the detail is the confirmation ("You're going!" → My tickets). `/orders/link/[token]` (email links) opens the web order page in the secure browser, since `/v1` has no route for an order held by a link.
- **Money and dates** are formatted per locale and currency with `Intl` (decimals from the currency: JPY none, BHD three); dates in the event's zone.
- **Accessibility:** every control has a role and label, 44 pt targets, wrapping text with no fixed heights, logical (start/end, `textAlign: 'auto'`) alignment; Arabic renders right to left; selected chips/steps show a mark and state, not colour alone.

## 3. Native dependencies and permission strings
- Added `expo-location ~57.0.21` (catalog `mobile`). Nothing else.
- iOS `NSLocationWhenInUseUsageDescription`: "Yayatoh uses your location once, when you tap "near me", to list events close to you." Android `ACCESS_COARSE_LOCATION`; `ACCESS_FINE_LOCATION` and `ACCESS_BACKGROUND_LOCATION` blocked. The Staff app asks for no location and blocks all three.

## 4. Not yet / Later
- **Organizer branding:** `PublicEvent` carries no brand colour yet, so `BrandScope` receives one only if the API adds `brandColor` (read defensively in `shop/text.ts`). Server gap; the event page uses the default theme meanwhile.
- **Short links:** no `/v1` route resolves a short code; the app follows the web's `/e/{code}` redirect (`HEAD`, reads the final URL). A `GET /v1/public/short-links/{code}` would replace it.
- **Order links from email** open the web page (no `/v1` route for orders held by a manage-link token).
- **Return to the event after sign-in:** checkout sends a signed-out person to `/` with `returnTo`; M7.3a's sign-in decides whether to honour it.
- Native payment sheet (Apple Pay, Google Pay), seat selection and checkout questions in the app (P7-12), refund requests from the order screen (M7.3b owns requests; this screen shows status), waitlist and access codes.
- The https return link inside an auth session: iOS before 17.4 cannot watch an https callback. The adapter falls back to the plain secure browser, and the return link reopens the app through the universal link; either way the order is read from the server. **Device pass.**
