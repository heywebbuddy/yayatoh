# Spec: M7.3d — Push and links

- **Milestone:** M7.3d (Phase 7 plan `docs/plans/mobile.md`, decision P7-8). Branch `agent/m7.3d`.
- **Status:** Built (2026-10-14) in `apps/mobile`, with one small addition to `packages/mobile-core`. No server code changed, so `pnpm test:int` was not run (see §7).
- **Risk tags:** `legal-copy` (the permission pre-prompt and the Notifications screen wording, in 13 locales), `mobile-contract` (the app now calls `POST/DELETE /v1/me/devices`)
- **Related ADRs:** 0010 (auth), 0025 (mobile apps). Builds on M7.2c (devices, push kinds, `data.path`) and M7.2d (associated domains).

## 1. Goal and users
A person with the Yayatoh app is asked for notification permission at the two moments P7-8 allows, never at launch, and in words that say what will be sent and what never is. Their phone is registered so the server's pushes reach it, and removed when they sign out. A tapped push, a universal link or an app-scheme link opens the right screen from a cold start, a warm start and the foreground. Saying no, anywhere, never blocks a purchase, a ticket or sign-in.

## 2. What was built
**Asking for permission** (`src/push/prompt-state.ts`, `components.tsx`, `provider.tsx`).
- Two moments, both outside launch: a purchase completing (the first one) and a ticket being opened (the first time ever). `reportPushMoment()` (`src/push/signals.ts`) is the one entry point; the provider also watches the route (`/tickets/{id}`) for the ticket moment, and the checkout return link reports the purchase moment itself (see §3). A moment that happens before the provider has mounted is kept.
- A pre-prompt (a modal) explains first: what is sent (order confirmed, ticket received or transferred, event changed or cancelled, reminders 24 h and 2 h before), that notifications never contain the person's name, email, phone number, payment amount or ticket code, and that they can change it in Account → Notifications. Only "Turn on notifications" shows the phone's own sheet.
- "Not now" stores the purchase count; the pre-prompt appears again only at a **later purchase**. Opening tickets never asks again. Once the phone has decided (yes or no) the app never asks: a refusal is changed only in the phone's settings, which the Notifications screen links to. Nothing in the app waits on the answer.
- State is a small JSON blob in secure storage (`yayatoh.push.prompt.v1`): purchases, whether the ticket moment was used, times shown, purchases at "Not now". Unreadable state starts over.

**Registration** (`src/push/registration.ts`).
- `POST /v1/me/devices` with platform (`apns`/`fcm`), token, `appId` (`expo-application`'s bundle id / package), `appVersion`, `locale` (the app's language), `timeZone`, and for APNs the `environment` (`sandbox` for development builds, `production` for preview and production, the same rule the `expo-notifications` plugin uses for `aps-environment`).
- Registers when signed in **and** the phone allows notifications. Registers again when the token, language, app version, time zone or person changes, when the OS rotates the token (`addPushTokenListener`), when the app returns to the foreground (the person may have changed the permission in the phone's settings), after a purchase (forced: the server answers `organizations: 0` until the person has an order or ticket), when the server last stored the phone nowhere, and at least weekly.
- `DELETE /v1/me/devices/{token}` at sign-out. `SessionStore.beforeSignOut()` (new, `packages/mobile-core`) runs the callback while the tokens still work, capped at 4 s so an offline sign-out still completes. A session the server ended (refresh token reused or revoked) cannot make the call; the row stays until the phone registers for someone else or the push service reports the token gone (see §7).
- Failures are silent and retried at the next start, foreground or purchase. Tokens appear only in secure storage and the request.

**Opening the right screen** (`src/links/incoming.ts`, `src/app/+native-intent.ts`, `src/push/routing.ts`).
- Links: Expo Router's `redirectSystemPath` (`+native-intent.ts`) runs for every incoming URL, cold or warm, and uses `routeForLink` (the path allowlist the server publishes): event, event short link, claim, ticket link, order link. A link on one of our hosts outside the allowlist opens Home; a URL that is not ours (the development client) passes through untouched.
- Pushes: `routeForPush(data)` accepts only `/tickets/{uuid}`, `/orders/{uuid}`, `/events/{slug}`. Cold start: `getLastNotificationResponseAsync` once the router is ready. Warm start and foreground: the response listener. A tap is handled once (a ledger by notification id), so Android's cold-start double delivery does not navigate twice.
- Sign-in: ticket, order, ticket-link and order-link routes need a signed-in person. Signed out, the target is kept (memory only, 30 minutes) and the person goes to the front door; the root layout opens it after sign-in. Claim and event links open at once (the claim screen explains the claim before it asks for sign-in).
- Checkout return link (M7.2f: `…/events/{slug}?checkout=return&order={uuid}`) opens `/orders/{uuid}` and counts as the purchase moment; `checkout=cancelled` opens the event.

**Foreground pushes** (`components.tsx`). A push that arrives while the app is open is drawn by the app (the system handler shows nothing): an alert-role banner with the server's title and body, scrubbed again with `scrubText` so an email address, phone number or long code could never be drawn; tappable only when its payload names a screen; dismiss button (44 pt); gone after 6 s.

**Notifications screen** (`src/app/account/notifications.tsx`, M7.3a links to it). The phone's state (on, off, not set up, checking) with the right button (Open phone settings, or Turn on notifications through the pre-prompt); what is sent; News and offers: "Off. We only send these if you choose to receive them."; "Notifications are optional. Tickets, orders and sign-in work the same with them off."

**Catalogs.** Namespace `push` in `apps/mobile/messages/*.json`, 13 locales (38 keys; no plurals needed). The Android channel name is translated.

**Config** (`packages/mobile-core/src/app-config.ts`, attendee app only): the `expo-notifications` plugin (`mode` development or production), the Android 13+ `POST_NOTIFICATIONS` permission, and `android.googleServicesFile` from `GOOGLE_SERVICES_FILE` (an owner file, never in the repo). iOS needs no usage string for notifications.

## 3. Choices made
- **Per-kind switches are not live.** The brief asks for switches for reminders and event changes. `/v1` has no route to store them, the server's `reminders` category is per organization and per email address (the web unsubscribe), event changes are `transactional`, and the push payload carries no kind, so a switch on the phone could not be honoured. Shipping switches that do nothing would be a consent problem, so the screen lists what is sent and, until a server increment exists, says "Choosing which of these you get is not available yet. To stop them all, turn notifications off in your phone's settings." The screen, the `PreferencesPort` and the save/rollback path are built and tested against a port that supports saving; enabling them is one adapter. Logged in `docs/owner-inbox.md`.
- **Marketing opt-in is not offered.** M7.2c deferred it to this increment, but no push marketing kind or consent route exists. The screen states it is off. The consent-ledger opt-in comes with the server route above.
- **The purchase moment** is reported by `reportPushMoment('purchase_completed')`; M7.3c's confirmation screen should call it, and the checkout return link does it already.
- **`beforeSignOut`** is an addition to the shared session store (additive, tested), not a wrapper around `signOut`, so every caller (M7.3a's account screen included) gets the deletion.

## 4. Permission strings
- iOS: none (notifications have no Info.plist string; the pre-prompt is the app's explanation).
- Android: `android.permission.POST_NOTIFICATIONS` (runtime permission on Android 13+).
- Native dependency added: `expo-notifications` `~57.0.23` (config plugin included; needs a development build).

## 5. Not yet / Later
- Per-kind switches and the marketing opt-in need `GET/PUT /v1/me/notification-preferences` over the existing suppression and consent-ledger machinery, and a `kind` in the push payload (owner inbox).
- A forced sign-out leaves the server row until another account registers the phone or the provider drops the token.
- Android small notification icon and accent colour (the default app icon is used).
- Device pass: real APNs and FCM delivery, the sheet on iOS 16.4+ and Android 13+, the tap from the lock screen, universal links verified by the OS, Maestro flows in `apps/mobile/.maestro/`.
