# Spec: M7.3b — Tickets (attendee app)

- **Milestone:** M7.3b (Phase 7 plan `docs/plans/mobile.md`, Wave 3; decisions P7-5, P7-7)
- **Status:** Built (2026-10-14), branch `agent/m7.3b`. App screens in `apps/mobile`; one small server route (`GET /v1/me/ticket-links/{token}`).
- **Risk tags:** `mobile-contract` (one `/v1` addition, owner approval before main), `legal-copy` (the calendar permission string). No migration.
- **Related ADRs:** 0002 (one command model), 0010 (auth), 0011 (QR and offline check-in), 0014 (allowlists), 0025 (mobile apps)

## 1. Goal and users
A signed-in attendee opens the app and finds their tickets: upcoming and past, grouped by event; the QR at the door in full brightness; where and when, in the event's own time zone; what they can do with the ticket (calendar, directions, wallet, transfer, refund). After one sync everything opens with the network off. A person who was sent a ticket claims it from the link. The app never signs or alters a code: it draws the string the server sends.

## 2. What was built
All code is in `apps/mobile/src/tickets/` (screens, hooks, services) and the route files named in `mobile-common.md`'s Wave 3 table: `(tabs)/tickets.tsx`, `tickets/[id].tsx`, `tickets/[id]/transfer.tsx`, `tickets/[id]/refund.tsx`, `tickets/link/[token].tsx`, `claim/[token].tsx`. Strings are in the `tickets` namespace of `apps/mobile/messages/*.json` (178 keys, 13 locales). Every call goes through `@yayatoh/sdk` by way of `core.api`.

| Area | Behaviour | Files |
|---|---|---|
| **My tickets** (`TicketsListScreen`) | Upcoming / Past tabs; tickets grouped by event and date (the group heading has the event's day, range and zone, organizer and a count); keyset paging with `onEndReached`; pull to refresh; "Last synced …" line; a "Transfer pending" tag; the organizer's accent colour on the card through `BrandScope` (contrast fallback in mobile-core); empty states (upcoming links to Discover); error with retry; offline note. | `screens/tickets-list.tsx`, `group.ts` |
| **Sync** (`syncTickets`) | One pass on tab open (skipped within 60 s), and on pull to refresh: walks every page of upcoming tickets (50 a page, capped at 20 pages), takes the first page of past ones, and fetches each ticket's full record (QR string, seat, entrances, transfer options) four at a time. A record is fetched again only when its `rev`, status or pending-transfer flag changed, or on a pull. Tickets that left the list (transferred away, refunded) are dropped with their record. The stamp only moves when every record was fetched. Offline, the pass does nothing. | `sync.ts` |
| **Offline** | Lists and records live in the core's encrypted query cache (XChaCha20-Poly1305 file, key in the keychain), so they are there with the network off. Detail queries that fail while offline keep showing the saved copy with a "saved copy" notice. `clearServerState` (sign-out, a dead refresh token) removes them and the key. | `hooks.ts`, mobile-core cache |
| **Ticket detail** (`TicketDetailScreen`) | The QR (react-native-svg from the `qrcode` encoder, level M, four-module quiet zone, black on white at every theme) with the spoken label "Ticket QR code for <event>"; the short code with a screen-reader label that spells it out; holder, type, seat, entrances and zones, event time in the event's zone, venue with address and access notes; organizer logo (alt text), name and "Powered by"; void and "event is over" banners; full screen brightness while the code is shown (restored on leaving, `useFocusEffect`). | `screens/ticket-detail.tsx`, `qr.tsx`, `services.tsx` |
| **Calendar, directions, wallet** | Add to calendar through `expo-calendar` (write-only access on iOS 17+, the system form, no read of the calendar; the notes carry the ticket type and organizer, never a code); directions through the venue's own https map link, then Apple Maps / a `geo:` link / the web map; "Add to Apple Wallet" (iOS) or "Save to Google Wallet" (Android) through `GET /v1/me/tickets/{id}/wallet` (the fake pass provider until the owner's accounts exist), with offline, unavailable and failure messages. | `services.tsx`, `ticket-detail.tsx` |
| **Transfer** (`TransferScreen`) | Name and email (the API's limits; your own address refused), a confirmation step, `POST …/transfers` with an `Idempotency-Key` (the same key on a retry of the same request, a new one when the recipient changes), "sent" with the recipient. A pending transfer shows on the ticket with a two-step cancel (`DELETE …/transfers/{id}`, keyed). `transfer.allowed`, the reason and the cutoff come from the API and are shown. **Transfer fee:** `web_payment_required` opens the returned link in the system's secure browser session (`expo-web-browser`) and refreshes the tickets when it closes. | `screens/transfer.tsx`, `ticket-detail.tsx` |
| **Refund requests** (`RefundScreen`, `RefundPanel`) | Reads the order behind the ticket and shows the refund policy (none / until a date / up to N days before / any time, and the retained fee), the latest request and its status (open, approved, declined with the reason) and, when `canRequest`, a form: which tickets (all by default, sent as "all"), an optional message. The refusal reasons the API gives (`request_open`, `policy_no_refunds`, `policy_window_closed`) are explained. `RefundPanel` is exported for the order screen (M7.3c). | `screens/refund.tsx` |
| **Claims** (`ClaimScreen`) | What is being claimed (sender, event in its zone, type, organizer), a name field starting from the account name, the claim with an idempotency key, then "View ticket". Signed out: the link is remembered in the keychain, the person is sent to sign in, and the Tickets tab brings them back (`PendingLinkResume`). A transfer sent to another address says whom it was for and offers "Use a different account" (remembers the link, signs out). Claimed, revoked and expired links, an invalid link, a rate limit and an unverified address each have their own message. | `screens/claim.tsx`, `pending.ts` |
| **Ticket links** (`TicketLinkScreen`) | A web "My tickets" link (`/my-tickets/{token}`) asks for sign-in, then `GET /v1/me/ticket-links/{token}` names the signed-in person's tickets for that event: one opens at once, several are listed. | `screens/ticket-link.tsx`, server route |

**Server addition.** `GET /v1/me/ticket-links/{token}` (operation `getMyTicketLink`, schema `TicketLinkTickets`): resolves a holder link with the web's `holderContext` and `holderTicketsQuery`, and returns `{ ticketIds }` only when the link's address is the signed-in person's verified address; an unknown, expired, tampered or foreign link is the same 404; no ticket code is returned. `apps/api/openapi.json` and `packages/sdk/src/schema.ts` regenerated, additions only.

**App config.** `@yayatoh/mobile-core/app-config` adds the `expo-calendar` plugin to the attendee app only (`writeOnlyAccess`, no reminders), with the permission string "Yayatoh adds the events you choose to your calendar."

## 4. Later / not yet
- **Maestro flows** (written in `apps/mobile/.maestro/`, not run: no simulator in cloud sessions): `tickets-open-offline`, `tickets-transfer-cancel`, `claim-from-link`, `ticket-link`, `refund-request`, and the shared `sign-in-email-code` sub-flow. Their sign-in steps follow M7.3a's screens and need a check when both are merged. Device pass.
- The sign-in route is `/welcome`, an assumption about M7.3a's welcome screen (`nav.ts`, `hrefs.signIn`); `hrefs.discover` is `/discover` (M7.3c). Both are string routes cast to `Href`, so a rename is a one-line change.
- A claim mismatch shows the recipient's name, not their address: the claim details never carry the address (`docs/owner-inbox.md`).
- Orders list/detail and checkout are M7.3c; push and link handling in the root layout are M7.3d. `RefundPanel` waits for M7.3c to embed it in the order screen.
- Multi-date wallet passes, "find my seat", the inbox: M7.6.
- Large ticket sets: the sync takes up to 1000 upcoming tickets; beyond that the rest load as the list is scrolled, online only.
- The QR is not rotated (ADR 0011: rotating codes are a later, owner-requested option).
