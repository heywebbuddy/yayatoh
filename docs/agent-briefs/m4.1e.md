## Scope (each fully tested)
- **A new `rsvp` form kind:** host-authored questions per event, optionally per sub-event ("Reception: meal choice", "Ceremony: song request"), with conditions (only if attending, only for adults, only if a plus-one is named).
- **Field types:** the engine's existing ones plus a **meal choice** bound to the event's menu options (with dietary notes).
- The answers are written back to the guest:
  - meal into `guests.meal`
  - dietary and accessibility answers into the sealed private fields
- **The RSVP page** asks the questions per guest in the household, after attending/declining, on a phone-first layout. Hidden questions' answers are dropped server-side.
- **Host side:**
  - a question builder with a live preview
  - meal counts per sub-event
  - an answers export (CSV with step-up; sensitive columns only for roles allowed to see them)
- Out of scope: the invitations sending (M4.1f), the caterer exports (M4.3b).

## Acceptance
- Conditional questions show and validate correctly in fixtures. Answers to hidden questions are rejected server-side.
- The meal choice lands on the guest. Dietary answers are sealed and never appear in logs, audit data or public payloads.
- Isolation; impersonation and freeze coverage.
- E2E on all three projects:
  - build questions with a condition
  - answer for a household of three, one of whom declines
  - meal counts update
  - keyboard only, axe, RTL
  - viewer can't edit questions
