## Scope (each fully tested)
- **Email code:**
  - `POST /v1/auth/email-code` requests a code. The response is the same whether or not the email exists, and requests are rate limited per email and IP.
  - `grantType: email_code` on `POST /v1/auth/token`: the first sign-in creates an account with the email verified; later sign-ins use that account.
- **Apple and Google:** `grantType: apple` and `grantType: google` verify a native id_token.
  - Check the signature against the provider's JWKS (cached, behind a port with a fake in CI), plus `iss`, `aud` (the app IDs, from env names added to `.env.example`), `exp` and the nonce (Apple carries the SHA-256 of the raw nonce).
  - Link to an existing account only through a provider-verified email, using the same rules as `social.ts`. An Apple private-relay email gets a new account.
- **Two-factor step:** when the account has TOTP, every grant returns `step_up_required` (`reason: two_factor_required`) with a single-use challenge that lasts 5 minutes. `grantType: two_factor` with the challenge and a TOTP or backup code issues the tokens.
- **Step-up on bearer sessions:**
  - `POST /v1/auth/step-up` takes an email code or TOTP and stamps the session.
  - `BearerSession` carries `stepUpAt`, and `orgScope` passes it into `ctx`, so commands with `stepUp: true` work over `/v1` within `STEP_UP_WINDOW_MS`.
- **`/v1/me` scope:** middleware for a signed-in person (a user bearer session with `emailVerified`; otherwise 403) that later increments mount routes on. `BearerSession.user` gains `emailVerified`.
- Regenerate `apps/api/openapi.json` and the SDK, and keep `pnpm contracts:check` green.

## Acceptance
- A two-factor account never receives tokens without a valid TOTP or backup code; a challenge works once and expires after 5 minutes.
- An id_token with a wrong audience, wrong issuer, bad signature, past expiry or mismatched nonce is refused; a valid Apple token with an unknown relay email creates a new account.
- Unknown and known emails get identical email-code responses; attempts are limited; codes expire.
- A `stepUp` command over `/v1` fails without a fresh step-up and passes within the window.
- Existing refresh rotation and family-revoke tests pass unchanged; oasdiff shows only additions.
