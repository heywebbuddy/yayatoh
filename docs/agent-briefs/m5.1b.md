# Task: M5.1b — Multi-page conditional forms (branch agent/m5.1b)

Read `docs/plans/phase-5.md` (approved; Wave 1, decisions P5-1, P5-8, P5-11), roadmap Phase 5 (M5.1) and §3.5, ADRs 0002, 0003, 0014 and 0016, `packages/modules/forms` (versioned definitions, the safe JsonLogic subset, server-side validation that drops hidden fields, the KeyVault envelope for sensitive answers, kinds `checkout_questions` and `survey`), the consent ledger (M1.5c2, `@yayatoh/crm` exports), `docs/specs/M1.5/spec.md` (guest verification and signed links) and the checkout-questions UI.

Built in parallel on Wave 1: M5.1a creates the `registration` module (registration types, admission items) and ADR 0021; do not create that module or any registration table, and do not write an ADR. Key per-type paths by an opaque registration type id supplied in the form's evaluation context (a string/uuid the caller passes), so M5.1a's types plug in at the Wave 2 wiring with no forms change. Do not build approvals, groups or invoices (Wave 2). **Add a new kind and pages without changing existing kinds**: `checkout_questions` and `survey` definitions, answers and tests must keep behaving byte-for-byte.

Scope (each fully tested):
- **`registration` form kind with pages**: ordered pages, each with fields and an optional page condition; conditions may reference answers on earlier pages; definitions stay versioned (a published version is immutable; submissions pin their version).
- **Per-registration-type paths**: a page (or field) can be limited to a set of registration type ids; the path is computed server-side from the type in context plus answers.
- **Server authority**: the server recomputes the visible path; answers on hidden pages or fields are **rejected** (not silently dropped) for the `registration` kind, with a `DomainError` naming the field; required fields on visible pages enforced.
- **New field types**: company lookup (suggests from the org's existing companies/contacts through public exports, free text allowed), job title list (org-editable list plus "other"), **consent checkbox bound to the consent ledger** (purpose and version from the ledger; checking records a versioned consent entry on submit, unchecked records nothing; this is how P5-8's "Exhibitors may receive my email" opt-in, default **off**, will be asked; its wording is `legal-copy`, so ship placeholder text and log it in `docs/owner-inbox.md`).
- **Save and resume by signed link**: a partial draft stored per respondent, a signed, expiring, single-respondent link (M1.5f rules) emailed through the existing notifications dispatcher; drafts expire and are purged; sensitive answers stay in the KeyVault envelope.
- Builder UI: pages, conditions and paths editable with the keyboard (move up/down buttons as the alternative to drag), a preview per registration type; respondent UI with a progress indicator and focus management between pages.
- Gate behind the `registration` module key (P5-1); the `conference_pack` `event_addon` entitlement is modeled by M5.1a, so do not add it here.
- House rules: every write through `tenantCommand`, allowlist serializers (the respondent payload carries only the visible path's fields), every new text/jsonb column in `private-columns.ts`, 13 locales + Arabic RTL, logical CSS, tokens only, strict CSP.

Tests: unit (path computation, cross-page conditions, hidden-answer rejection, consent field mapping), property test (the server's path equals the client's for random answer sets), integration (**a fixture path shows and validates exactly the right pages for three registration types**; answers on hidden pages rejected; consent entry written with the ledger version; resume link expired/forged refused; existing kinds unchanged; isolation with `createOrgFixture` rows for both orgs in every new table), e2e with keyboard, axe and Arabic RTL: build a three-page form with a type-specific page, fill it as two different types, save, resume from the emailed link (Mailpit), submit; viewer `jordan@lakeside.test` cannot edit the definition.
