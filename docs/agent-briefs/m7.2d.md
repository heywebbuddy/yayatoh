## Scope (each fully tested)
- **`/.well-known/apple-app-site-association`** (no extension) and **`/.well-known/assetlinks.json`**, both `application/json`, never redirected.
  - Served on `yayatoh.com`, `app.yayatoh.com` and tenant subdomains of `TENANT_APEX`, but not on custom tenant domains (they can't be in the app's entitlements).
  - Built from env (`.env.example` names): the Apple team ID, each app's bundle ID and Android package per environment, and the Android signing SHA-256 fingerprints.
  - A path allowlist: ticket, order, claim and event pages, plus staff enrolment.
  - `webcredentials` for password autofill.
  - Make sure `proxy.ts`, the front door, locale redirects, auth redirects and Caddy don't intercept these paths.
- **Enrolment QR:** the device-enrolment screen also shows the enrolment link as a QR. The link is a universal link the Staff app claims and still opens the Scan PWA in a browser. The token stays in the URL fragment: it is never sent to the server or logged.
- **Version enforcement:**
  - Middleware on `/v1` parses `X-Yayatoh-Client` (the four identifiers from P7-9 and M7.1c).
  - A version below its app's minimum gets `426` problem+json with the store URL.
  - Device routes never return 426 inside the device's event window (24 h before start to 2 h after end).
  - A missing or unknown header always passes (web and integrations).
  - Per-app minimums are added to `MobileSettings` and `/v1/mobile/config` as new fields; the existing fields stay.

## Acceptance
- Both files return 200 `application/json` without a redirect on each supported host, and 404 on a custom tenant domain.
- A below-minimum attendee app gets 426 with a store link; a below-minimum Staff device gets no 426 during its event window; requests without the header are never refused.
- The enrolment QR decodes to exactly the text link, and the token never appears in server logs.
- The existing e2e specs for hosts, the front door, security headers and the Scan PWA pass on all three projects; oasdiff shows only additions.
