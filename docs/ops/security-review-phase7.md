# Phase 7 security review: the mobile apps (M7.x)

Scope: the attendee app (`apps/mobile`), the Staff app (`apps/staff`), `packages/mobile-core`, and
what Phase 7 added to `/v1`: app sign-in (email code, Apple and Google id_tokens, the two-factor
step, step-up), `/v1/me/*` and `/v1/claims`, native push registration, the public search and the
apps' checkout, the Staff device routes, the exhibitor portal routes and the organizer's event-day
view, `DELETE /v1/me`, and the link and version files. Method: code review of the merged Wave 1–3
code, adversarial tests for the parts a reviewer can attack from a script, and the leak test of
`docs/specs/M7.X/spec.md`. Nothing ran on a phone, so what only a device can show is listed at the
end. No real Expo, Apple, Google, APNs, FCM or Sentry account was used. Written in general terms on
purpose (the repo is public).

**Result: no open high finding.** Two medium findings and two low ones are fixed on this branch,
each with a test. Four medium findings stay open with an owner. The reviewer demo (M7.5a) did not
exist on this branch; its guard is a checklist (section 4), not a verdict.

|---|---|---|---|---|
| O1 | Medium | **A lost refresh response signs the person out and wipes their data.** The server spends the refresh token before the response arrives. If the response is lost (a tunnel, a venue's Wi-Fi), the app still holds the spent token, tries it on the next request, and the server treats that as a theft: it revokes the whole family and the app wipes its tickets. Rare per refresh (every 15 minutes), certain across a crowd, and at a door the person cannot sign in again without a network. | A short reuse window (10–30 s) in `refreshTokenService.rotate`: a spent token presented again within it, from the same family and with no later child used, gets a new child instead of a revoke. ## 3. Hardening, not exploitable today
- **Custom URL schemes** (`yayatoh-staff://scan#…`) can be claimed by another Android app. The enrolment QR holds the `https` universal link, not the scheme link, so nothing sends a key through it; the scheme exists for development builds. Do not generate scheme links for enrolment.
- **Server-supplied URLs are opened without a scheme check** (`paymentUrl`, `webUrl`, wallet links). The server builds them over TLS and organizer-controlled links (maps) are already `https`-only (`safeHttpsUrl`). Add the same check to the payment, web and wallet openers (development builds need `http` for the fake provider, so it is a per-environment rule).
- **An id_token can be replayed within its lifetime** (the nonce is chosen by the app, not issued by the server, and `jti` is not recorded). Replaying needs the token, which lives only in the app for a few seconds. Record `(sub, nonce)` for the token's lifetime if it ever matters.
- **A rep's unsent leads stay on the phone** (encrypted, owner-scoped) after they sign out, until they sign in again or the device is wiped. Intended (nothing is lost), but say it in the privacy answers and clear queues older than 90 days.
- **Native crash reports** (an app killed by the OS) are written by Sentry's native layer and may not pass the JavaScript `beforeSend`. `sendDefaultPii` is off and no user is set, but confirm in the device pass that a test crash carries no breadcrumb text.
- **Event names on the lock screen.** Push text is the event name and a fixed phrase (P7-8). A private event's name is shown to anyone who sees the lock screen; organizers choose those names.
- **Rate limits per person** (600 requests a minute per signed-in user, 3 000 for a door device) are in-memory per instance; the sign-in and checkout limits are shared (S1, M7.2f). Moving the credential limit to the shared store is the follow-up.
- **The two-factor challenge counts wrong codes with a read-then-write.** Parallel guesses can exceed five; the per-person pause (5 wrong codes in 15 minutes, in the database) and S1's shared limit bound them. Make the increment atomic when the challenge moves to its own table.

## 4. The reviewer demo (M7.5a): what must hold at merge
The demo is the one place Phase 7 adds a deliberate shortcut. When `agent/m7.5a` merges, check each line (and add a test if the branch lacks one):
- The seeding script refuses to run when the database is production (`isProductionEnv()`, the platform flags and `NODE_ENV`), and says why.
- A fixed email code for the reviewer address exists only in the fake mailer, which production never builds; the real mailer path has no address-specific branch (grep the auth package for the address and for `fixedCode`).
- The reviewer attendee has no step-up or deletion exemption; deleting the demo account works like any other.
- The Staff enrolment link is for the demo org's own device token: revocable, event-scoped to the demo event and expired after the review window.
- The demo org is never listed in the marketplace, sitemaps or search (D13: private), and sends no real email or push.
- The listing's review notes contain no real credential: only the instruction to use the email code shown in-app or in the notes, in non-production builds.

## 5. Checked, no finding
- **Token storage.** Access and refresh tokens live in one keychain item (`AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`); they leave it only in an `Authorization` header (`session-store.ts`). Memory is updated before the write, so a spent refresh token is never reused after a failed write. One refresh at a time; a second 401 waits for the first. A 401 on refresh ends the session and wipes; a network error or 5xx does not.
- **Refresh rotation on the server.** Hashes only (SHA-256), 256-bit tokens, the spend is a single conditional `UPDATE` (of two requests with one token exactly one wins), reuse revokes the family and ends its access sessions, a password change or "sign out everywhere" revokes every family, and a refresh keeps the old step-up instead of renewing it. See O1 for the cost of that strictness.
- **Cache and manifest encryption.** The query cache is one XChaCha20-Poly1305 file with the header as associated data and a fresh 24-byte nonce per write; the key is in the keychain and wipe deletes the key first. The Staff manifest is SQLCipher with a raw 256-bit key from the keychain; a file the key cannot open is deleted. The tools' vault (guest list, check-in and lead outboxes) is sealed the same way, wiped with the device, and lead queues are scoped to their rep. Nothing sensitive is written with `AsyncStorage`, plain files or a plain database (grep over `apps/*/src` and `mobile-core/src`). S2 closes the one plaintext copy the networking stack could make.
- **Links.** `routeForLink` accepts `https` on the platform hosts and `{slug}.<tenant domain>` (one label, no userinfo, port or encoded separators) and the app's own schemes, then a path allowlist with strict segment shapes; Expo Router params can only fill the declared segments. The adversarial list in `links.test.ts` (look-alike hosts, `@` and `%40` tricks, ports, `http`, `intent:`, `javascript:`, traversal, doubled segments, other apps' schemes) all fail to route. The Staff enrolment key is read only from the fragment, cleared from the route after one read, and only ever sent to the configured API. A push `data.path` opens a ticket, an order or an event and nothing else.
- **Logs and crashes.** No `console` output outside `__DEV__` and durations. Sentry is off without a valid DSN; with one: no default PII, no screenshots or view hierarchy, no tracing, and `beforeSend` and `beforeBreadcrumb` drop the user, headers, cookies and bodies, strip query strings and identifier-like path segments, and mask emails, phones, tokens, JWTs, hex and ticket codes. Tokens never appear in an error message (`reportError` scrubs the text).
- **Push content.** Eight kinds, push-only; title and body are checked in all 13 locales against a name, email, phone, amount, code and URL (`app-push-copy.test.ts`). A phone is stored only for organizations where its owner has an order or ticket, and registering a token removes it from anyone else.
- **Sign-in.** Email-code requests answer the same for known and unknown addresses; a code is single use with a lock after wrong tries; Apple and Google tokens are checked for signature (RS256 only), issuer, audience, expiry, issue time and nonce, and the fake verifier cannot run in production; a provider email that matches an existing account needs a proof by emailed code; an unverified account is reset before an emailed code can claim it. Two-factor accounts get a challenge instead of tokens on every first factor. Account deletion needs a fresh step-up and is refused under impersonation.
- **Tenant isolation of the person routes.** A person is their verified email and nothing in a path or body names whose tickets these are; ids from another person are the same 404 as unknown ones (`me-tickets.int.test.ts`); `/me/*` needs a verified email. The leak test (`canary-mobile.int.test.ts`) reads every Phase 7 route with each credential against an org with a canary in every private column.
- **Checkout.** Return and cancel links are built on the server from the configured web origin; the app opens only what the server returns, over TLS. Virtual and streamed passes are refused; carts that need the web get the web checkout address.
- **Connector-free builds.** With no Sentry DSN, Google client id, Firebase file, EAS project, owner or store key, both apps configure and build, and each connector is off; `eas.json` names profiles only; `.env.example` holds one live line; no source file holds a key, a DSN or a token (`connector-free.test.ts`). Plain `http` is refused outside development builds. `EXPO_TOKEN` is read only by the Maestro workflow, from a GitHub secret.
- **Version gate.** `X-Yayatoh-Client` is not a security boundary: a request without it is never refused (by design), and a Staff device is never refused inside its event window.
