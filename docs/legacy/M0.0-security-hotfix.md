**Applies to:** the live Laravel app behind **yayatoh.com** and **abc.yayatoh.com** (same codebase, `gitlab.com/eventmie-pro/abc-web`).
**Found by:** read-only code audit, 2026-09-26. Every item below was found by reading the code. Items 1, 2 and 5 were re-checked by hand at the file lines shown.
**Priority:** fix P0 items within 24–48 h. They are exploitable today without any login.

## P0 — fix first (account takeover and free tickets)

### 1. Forged Google/Apple login → takeover of any account, including admin
- **Where:** `app/Http/Controllers/Api/v2/Auth/SocialLoginController.php:59-70` (Google), `:95-127` (Apple).
- **Problem:** `social_token` is split on `.`, and the payload is `base64_decode`d **with no signature check**. Then `User::updateOrCreate(['email' => $data['email']], [... 'role_id' => 2])` runs. Anyone can craft a token with any email and log in as that user. It also demotes the victim to `role_id` 2, which breaks admin accounts.
- **Fix:**
  1. Disable the route immediately (`POST /api/v2/social-login`, `routes/api/v2/index.php:139`), **or** verify the token:
     - **Google:** use `google/apiclient` `verifyIdToken()`, or fetch Google's JWKS and verify with `firebase/php-jwt`. Check `aud` equals your client IDs, `iss` is `accounts.google.com` or `https://accounts.google.com`, `exp`, and `email_verified`.
     - **Apple:** verify against `https://appleid.apple.com/auth/keys`. Check `aud` equals your bundle ID / Services ID, `iss` is `https://appleid.apple.com`, and `exp`.
  2. Never overwrite `role_id` for an existing user. Set role 2 only when creating a new user.
- **Verify:** a token with a forged signature returns 401; an existing admin logging in via Google keeps `role_id` 1.

### 2. Stripe webhook signature check disabled → forged "paid" bookings
- **Where:** `app/Http/Controllers/WebhookController.php:9-12`.
- **Problem:** an empty `__construct()` overrides Cashier's constructor, which is where the `VerifyWebhookSignature` middleware is registered. A forged `checkout.session.completed` carrying a known `client_reference_id` (the buyer can see it in `success_url?orderId=`) creates a paid booking via `app/Listeners/StripeEventListener.php`, then `FailedPaymentController::WebhookStripeMakeBooking`.
- **Fix:**
  - Delete the empty constructor, or call `parent::__construct()`.
  - Make sure the webhook secret is configured: `cashier.webhook.secret` / the Voyager `apps.stripe_webhook_secret_key` setting.
  - Also retrieve the Checkout Session from Stripe in the listener. Use the `stripe_account` option for connected organisers, and require `payment_status == 'paid'` before booking.
- **Verify:** a request without a valid `Stripe-Signature` returns 403; a real test-mode checkout still books.

### 3. Flutterwave and Mesdoh accept a forged "success"
- **Flutterwave:** `app/Service/Flutterwave.php:112` (callback) and `:183` (webhook) trust `status=='successful'` from the request. There is no verify API call and no `verif-hash` check, and both are CSRF-exempt.
  - Because `failed_booking()` stores every checkout, a forged Flutterwave webhook can complete **a Stripe or PayPal order that was never paid**.
- **Mesdoh:** `app/Service/MesdohService.php:105-128` treats `?status=success|completed|approved|paid` in the **buyer's own redirect URL** as proof of payment. `mesdoh_api_secret` is never used.
- **Fix:**
  - Flutterwave: call `GET /v3/transactions/{id}/verify` and check amount, currency and `tx_ref`. Check the `verif-hash` header on webhooks. Only complete orders whose `payment_gateway` is Flutterwave.
  - Mesdoh: call Mesdoh's server-side status API with the secret before approving. If none exists, **disable Mesdoh** (payment code 12).
  - **If either gateway is not in use, disable it** by clearing its `apps.*` settings.
- **Verify:** hitting the callback with `?status=success` and no real payment creates no booking.

### 4. Any organiser can take over any user
- **Where:** `app/Http/Controllers/SubOrganizerController.php:53-83`.
- **Problem:** changes any user's email, including user 1 (admin), with no ownership check. Changing the email and then using password reset gives full takeover.
- **Fix:** only allow editing sub-organisers whose `organizer_id` is the current organiser, and never users with role 1 or 3.
- **Also:** `Route::impersonate()` (`routes/web.php:1048`) with no `canImpersonate()` / `canBeImpersonated()` override on `App\Models\User`. With lab404's defaults, **any logged-in user may impersonate anyone** (verify on staging).
  - Add `canImpersonate(): bool { return $this->role_id == 1; }` and `canBeImpersonated(): bool { return $this->role_id != 1; }`.
- **Also:** `/admin/failed-bookings/{order_id}` (`FailedPaymentController.php:174-178`) lets any organiser force-create a booking with no payment. The list (`:44-62`) shows every customer's email and phone. Restrict it to admins.

### 5. Order numbers are QR codes and they leak
- **QR payload:** the ticket QR is the raw `order_number`, or JSON `{id, order_number}`. The scanner uses only `order_number`, so **knowing an order number is enough to get in**.
- **Leaks:**
  - `GET /api/v2/generate-pass/{booking_id}` (`app/Http/Controllers/PassController.php`, route `routes/api/v2/index.php:280`) has **no auth**. It returns an Apple Wallet pass (barcode = `order_number`) for any booking ID and saves it publicly under `storage/passes/`.
    - **Fix:** require `auth:sanctum` and check that the booking belongs to the user (or that they are the event's organiser). Store passes privately.
  - Public attendee search `/events/{slug}/attendee/search` (`app/Http/Controllers/Eventmie/PublicEventController.php:44-151`) returns names, masked emails, **unmasked `order_number`s** and **`private_info`** to anyone. It doesn't even check `enable_public_seating`.
    - **Fix:** require `enable_public_seating`; drop `order_number` and `private_info` from the response; minimum 3 characters; rate-limit (for example 20/min per IP + event).
  - Event show/details payloads carry attendee rows with booking `order_number`s (see item 6).

### 6. Public API leaks organiser data, private info and attendee PII
- **Root causes:**
  - `app/Models/Event.php:132, 266, 303, 344` use `with(['user'])`, which loads the **full** organiser row.
  - `app/Models/User.php:32-35` `$hidden` only covers `password` and `remember_token`.
  - `Event.php:23` `$hidden` omits `private_info`.
  - `app/Helper/helpers.php:13-16` overrides `view()` so that under `api/v2` **every view variable is dumped as JSON**.
- **What leaks:**
  - organiser bank/tax fields, Mailchimp API key, `magic_login_token` (a 72-hour login link), Stripe IDs, FCM/APN tokens, email, phone, address
  - the event's `private_info` (Wi-Fi password, parking code, contact)
  - reviewers' full rows (`EventsController.php:695-728`)
  - attendee name/phone/address and booking `customer_email` + `order_number` via `app/Models/Ticket.php:40-56` (eager-loads `attendees`, `attendees.booking`, `promocodes`)
  - the same data embedded in `events/show.blade.php:221,232`
- **Password-protected and unpublished events** are fully readable via `/api/v2/events/show/{slug}` and `/api/v2/events/details`.
- **Endpoints affected:** `/events/api/get_events`, `/api/v2/events`, `/api/v2/landingPage`, `/api/v2/events/show/{event}`, `/api/v2/events/details`, `/api/v2/venues/{slug}`, `/api/v2/organiser/{url}`, `/{organisation_url}`, `/api/get/events`, and the event web page.
- **Fix — do the order carefully:**
  1. **Ship first:** an authenticated `/api/v2` endpoint that returns `private_info` only to users with a booking or event-code join for that event. Today the only such route is the **web** route `/api/events/{id}/private-info` (`routes/web.php:859`), which bearer tokens can't use. The mobile app probably reads `private_info` from the leaking payload, so without this step the app's private-info screen breaks. Then update or check the app.
  2. `Event.php:132,266,303,344`: change to `with(['user:id,name,avatar,organisation,organisation_url'])`. `EventsController.php:166-167`: add the same `->select(...)`.
  3. `User.php` `$hidden`: add `bank_account_name, bank_account_number, bank_account_phone, bank_code, bank_name, bank_branch_name, bank_branch_code, taxpayer_number, seller_name, seller_info, seller_tax_info, seller_signature, mailchimp_apikey, mailchimp_list_id, magic_login_token, magic_login_expires_at, stripe_id, stripe_account_id, pm_type, pm_last_four, fcm_token, apn_token, apple_id, ip_address, settings, organizer_id`. Keep `email` and `phone` visible only where the owner needs them: `/api/v2/user` and profile.
  4. `Event.php:23`: add `private_info` to `$hidden`. Remove or gate `$extra['private_info']` at `EventsController.php:194`.
  5. `EventsController.php:697,726,728`: change to `with('user:id,name,avatar')`.
  6. `Ticket.php:44-45`: limit to `attendees:id,ticket_id,seat_id,booking_id,event_date` and `attendees.booking:id,status,event_start_date,event_start_time`. That is all the seat map reads (`Seat.vue:256-266`, `PublicSeat.vue:169`). Drop `promocodes`, or pass only a count. Do the same at `EventsController.php:434`.
  7. In `EventsController@show` and `@details`: enforce the password/unpublished check on API requests, not just the web view switch at `:222-233`.
- **Verify:** a CI or curl check over the endpoints above finds none of those keys. The mobile app still shows events, the seat map, bookings and private info (for ticket holders) on staging.

### 8. Kill outstanding magic-login tokens
