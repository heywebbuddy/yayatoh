Admin: Voyager BREAD for everything, settings tabs (Site, AI, Storage, SEO, Social, Contact, Booking, Multi-vendor, Admin, Payments, Apps, Mail, Regional). **Open questions.** Eventmie license/support contract constraints; whether the three hosts are separate DBs/codebases; whether AI prompt credits monetisation is kept; whether the root-level organizer URL must be preserved exactly.

## 2. Multi-tenant

**Exists today.** No true tenancy: `organizer_id` parent on users for sub-organizers, `organizer_users` pivot per event; each white-label tenant is a separate install with its own DB, overlapping IDs (event ids 26–28 exist on both hosts with different content), its own Voyager settings/posts and its own store-published app.

**Recommended approach.** One shared Postgres 18 (move to 19 for `REPACK CONCURRENTLY` when GA, expected end Oct 2026), `org_id uuid NOT NULL` on every tenant-owned row, Postgres RLS as backstop with app-level scoping via a server-only DAL (`db.forOrg(ctx)`, no un-scoped builder) as primary. RLS rules: `ENABLE` + `FORCE ROW LEVEL SECURITY`; runtime role `app_user NOBYPASSRLS` distinct from migrator/owner; policy `org_id = (SELECT current_setting('app.org_id', true)::uuid)` (the `(SELECT …)` wrapper avoids the ~575× regression seen on 10M-row tables); every index leads with `org_id`; composite FKs `(org_id, parent_id)`; uniqueness scoped `(org_id, slug)` (global uniques leak existence across tenants); `STABLE/LEAKPROOF` policy functions; views with `security_invoker = true`; `SECURITY DEFINER` functions with `SET search_path = ''`; context set inside the transaction via `set_config('app.org_id', $1, true)` / `SET LOCAL` (safe under PgBouncer/Neon/Supavisor transaction pooling; RDS Proxy pins on `set_config` — `SET LOCAL` non-pinning for Postgres UNVERIFIED — so avoid RDS Proxy). Migrations over a direct connection as owner. Roles: `app_user`, `migrator`, `platform_reader` (`BYPASSRLS`, super-admin console and cross-org analytics only, every use logged). Rejected: schema-per-tenant (migration fan-out failures, catalog bloat, `search_path` not pooler-safe), database-per-tenant as default (pool fan-out, no cross-tenant discovery); keep a `shard_key`/`database_ref` seam on `organizations` for a future dedicated-DB enterprise tier. Nile is a credible managed alternative but locks in the database. ORM: Drizzle 0.45.3 (1.0 rc.4) declares `pgRole`, `pgPolicy`, `.withRLS()` in schema; Prisma 7 runner-up loses because its RLS extension breaks explicit `$transaction` and Prisma 8 replaces client extensions. Org membership via Better Auth 1.7.6 `organization` plugin (invitations 48 h default, `membershipLimit` default 100 — raise, dynamic roles) plus `org_relationships(parent, child, kind)` for agencies and `event_grants`/`event_role_assignments` for event-scoped staff (door staff, seating manager, session scanner, exhibitor rep). Contacts/attendees are org-owned CRM rows with optional link to a global `users` row — never global attendee records. CI-gated isolation suite: two-org fixture through app role and pooled path, adversarial raw-SQL test, generated API tests for a dual-org user (other org's ids → 404), schema guard asserting `relrowsecurity`/`relforcerowsecurity` on every `org_id` table, cache guard rendering one route for two tenants. Migration backfill: one organization per existing organizer, stamp `organization_id` via event→owner chain, quarantine orphans (shared venues, global attendees) in a report.

**Key entities.** organizations (slug, plan, type, settings, theme, default_locale, powered_by_visible, shard_key), memberships, invitations, org_roles/permission sets, event_role_assignments, org_relationships, platform_staff, impersonation_sessions/support_sessions, audit_log, org_modules/org_module_entitlements, contacts.

**Risks.** RLS performance regressions; cross-tenant cache bleed if tenant read from headers instead of root params; new tables defaulting to RLS off; `platform_reader`/impersonation as attack surface; ID remapping across two live DBs; ABC convention in progress (Sept 2026) with active scanning.

**Open questions.** Should venues stay a platform directory or become org-owned? Is `/events` marketplace opt-in per org/event? Do agencies need detachable child orgs? Any enterprise needing dedicated DB/region in 18 months? Global attendee account across organizers vs org-scoped accounts on white-label domains?

## 3. White-label

**Exists today.** Per-install branding via Voyager settings, "Powered by https://yayatoh.com" footer, subdomain `abc.yayatoh.com`, per-tenant mobile app, Mailchimp keys per organizer, Blade email templates global.

**Recommended approach.** Tenant public surface resolved by host in `proxy.ts`: exact custom domain → `<slug>.<tenant-apex>` → 404; delete inbound `x-tenant-*` headers; rewrite to `app/t/[org]/…` so tenant is a root param and part of `use cache` keys; tag caches `org:<id>` and revalidate by tag (never `revalidatePath` on public paths; proxy does not run for on-demand ISR). Lookup store: Vercel Global Config (renamed from Edge Config 2026-07-29; ~1 ms, 1 MB/store) or Upstash Redis + in-process LRU. Serve tenant sites from a **dedicated apex** (e.g. `*.yayatoh.events`, availability UNVERIFIED) and keep dashboard/auth on `yayatoh.com` with `__Host-` cookies; submit the apex to the Public Suffix List early; existing `abc.yayatoh.com` kept as a custom domain/301. Custom domains: Vercel Domains API (unlimited on Pro, soft 100k/project, no per-domain fee, Let's Encrypt auto; rate limits 100 adds/h/team, 50 verifications/h, 100 removals/h → provisioning queue); Cloudflare for SaaS (100 hostnames free, $0.10/hostname/mo, 50,000 max self-serve; Host-header override Enterprise-only, so it cannot front Vercel) or Caddy on-demand TLS (`ask` endpoint; LE limits 50 certs/registered domain/week, 300 orders/3 h) only if origin leaves Vercel. Domain lifecycle `pending_dns → verifying → active → failed`; each domain must also be registered with Stripe's Payment Method Domains API or Apple Pay/Google Pay/Link silently disappear. Theming: validated per-org theme JSON (primary, onPrimary, surface, radius, fontFamily, logo, favicon, darkMode) rendered as cached CSS variables in the `/t/[org]` layout; Tailwind 4.3 tokens map to them; contrast-safe derived tokens computed server-side (enforce ≥4.5:1 in the brand picker); `icon.tsx`/`opengraph-image.tsx` per org; curated `next/font` allowlist; React Email templates from the same tokens with `(org_id, template_key, locale)` overrides; `org_navigation` JSON + module flags; "Powered by" toggle by plan; per-org legal pages and support email. Sessions across apexes: central login on `yayatoh.com` → single-use 60-second host-bound code → `events.org.com/auth/callback` sets `__Host-session`; Better Auth `trustedOrigins` function form UNVERIFIED. Passkeys register on the central rpID. Email: Amazon SES v2 Tenants (one SES tenant per org, subdomain delegation `mail.<org-domain>` with Easy DKIM 3 CNAMEs + custom MAIL FROM; fall back to `orgslug@mail.yayatoh.com`; 10,000 identities/Region; API throttled 1 req/s for non-send actions); Postmark runner-up; Resend disqualified by domain caps (Scale 1,000, +100 for $20/mo). Mobile: single app with org picker and runtime theming (Apple 4.2.6 blesses the aggregated model; Google Play repetitive-content policy); per-tenant builds via Expo EAS `APP_VARIANT` only as premium tier under the client's own developer accounts; deep links stay on the platform link domain because iOS associated domains need each apex in the entitlement (wildcard `applinks:*.yayatoh.events` support UNVERIFIED); serve AASA/assetlinks per tenant host.

**Key entities.** org_domains/tenant_domain (hostname, kind, is_primary, verification_status, token, provider_ref, ssl_status, payment_method_domain_id, wallet_enabled, csp_frame_ancestors), tenant_theme, org_navigation, org_email_templates/message_template, org_email_domains/sending_domains, embed_domains, app_versions.

**Risks.** Cookie leakage between tenant subdomains and dashboard until PSL; Vercel domain rate limits stalling migrations; hosting move changes the entire custom-domain strategy; tenant DNS friction for DKIM/MAIL FROM/DMARC.

**Open questions.** Commit to Vercel or plan self-host from the start? Dedicated apex acceptable? Which tier gets custom domain/email domain/"Powered by" removal and at what price? Branded apps for tenants?

## Consolidated risk register (top 20)

1. **Cross-tenant data leak** (un-scoped query, table without RLS, cache keyed without tenant). Mitigation: forced RLS + DAL + CI schema guard + generated two-org route suite + cache guard as merge blockers.
2. **Breaking a shipped mobile app** (unnamed routes, pinning, 503/426 handling). Mitigation: route enumeration from `routes/api.php`, golden HAR, legacy facade at exact `/api/v2` paths, Sanctum token compatibility, bridge build before any cutover, telemetry-gated sunset.
3. **Offline scanning promised but unverified in the current app**; ABC convention live in Sept 2026. Mitigation: read app source before promising parity; PWA + manifest/sync design; dual-verification of legacy QR.
4. **Data migration defects** (timezone shift from America/New_York DATETIME, case-insensitive duplicates, zero dates, JSON blobs, overlapping IDs across two DBs). Mitigation: ELT with explicit casts, ≥3 rehearsals, validation suite with golden queries, point-of-no-return with reverse ETL.
5. **Payment continuity and loss liability** (Connect accounts, pending manual settlements, event cancelled after payout, dispute clock at event date). Mitigation: same Stripe account, pre-registered webhook, payout tiers/reserves, `debit_negative_balances`, fee reconciliation.
6. **Seat/ticket oversell under load** (inventory or session capacity race, stale Redis holds). Mitigation: Postgres conditional updates/row locks/advisory locks, hold reconciler, atomic session enrollment, waiting room.
7. **Critical Next.js/React CVEs** (CVSS 9.5–10 RCEs in the last year). Mitigation: 24-hour patch SLA, DAL-based authz, isolated image processing.
8. **SEO traffic loss** (URL changes, missing redirects, preview noindex, broken JSON-LD). Mitigation: same-domain URL parity, DB redirect map ≥1 year, sitemap/canonical/hreflang, GSC monitoring.
9. **White-label cookie/session/CSP fragmentation** (subdomain cookie leakage, passkey rpID, wallet domain registration). Mitigation: dedicated tenant apex + PSL, central auth handoff, Payment Method Domains registration in domain onboarding.
10. **Hosting-constraint lock-in** (Vercel 800 s/4.5 MB/WS beta; Cloudflare cannot front Vercel). Mitigation: containerized api/worker, Ably, presigned uploads, decide edge once.
11. **Messaging compliance exposure** (TCPA $500–1,500/text, TX $5,000, quiet hours, revocation rules moving; WhatsApp US marketing pause; 10DLC latency). Mitigation: consent ledger and policy gate in the pipeline, platform + tenant sender tiers, SMS fallback.

13. **Seating canvas scope creep / performance** (built three times, per-seat nodes blanking iPads, destructive edits after sale). Mitigation: one `@yayatoh/floorplan` package, batched shapes + LOD, locked event layouts with stable seat_uuid.

## Contradictions between reports and resolutions

1. **Stripe charge type and loss liability.** Payments report: destination charges + `on_behalf_of`, `losses.payments=application` (platform liable), direct charges as phase-2 BYO. Security and multi-tenant reports: direct charges on the connected account with Stripe responsible for negative balances. Resolution: adopt the payments report (destination + on_behalf_of, application liable) because platform Radar, cross-org reporting, wallet-domain registration and the Command Center depend on platform-side PaymentIntents, and Stripe says not to assign Stripe liability when charging on the platform; offset liability with payout tiers, reserves and `debit_negative_balances`. Keep direct charges as an enterprise option. Owner must confirm risk appetite.
2. **API version naming.** Multi-tenant report freezes the existing contract as `/api/v1` and adds `/api/v2`; migration report calls the compat API "v1"; integrations/stack reports use `/legacy` + `/v1`. Fact: the current mobile contract lives at `/api/v2/*`. Resolution: the legacy facade must reproduce the exact `/api/v2/*` paths on `yayatoh.com`; the new API is `api.yayatoh.com/v1`; never label the facade "v1".
3. **QR token format.** Offline report: Ed25519 binary/base32 per-org key with `kid`; security: per-event Ed25519 keys + rotating TOTP; migration: HMAC `YT1.<uuid-base32>.<sig>`; integrations: `yy1.` base64url ~120 chars. Resolution: Ed25519 compact binary (offline report) with per-org keys and `kid` rotation (per-event keys optional via `kid`), `ticket_rev` = `barcode_version`; reject HMAC because offline devices would need the secret; TOTP as optional Secure Ticket mode.
4. **Password rehash target.** Stack report: scrypt (Better Auth default); migration: argon2id or bcrypt-12; security: Argon2id (NIST). Resolution: Argon2id via Better Auth custom `password.hash`; scrypt acceptable only if the custom hook proves problematic.
5. **Real-time transport.** Offline: Ably via outbox → Redis Stream → worker; seating: Redis pub/sub → SSE; analytics: delegated; stack: Ably or a Fly ws box. Resolution: one `RealtimePublisher` (Ably primary, SSE fallback) shared by seat availability, check-in feed, Command Center and in-app notifications; Supabase Realtime only if Supabase is the DB (it is not — Neon).
6. **Queue engines.** Marketing/stack/analytics: Inngest; integrations: BullMQ per-connection queues; analytics: pg-boss/graphile-worker for the projector. Resolution: Inngest for durable workflows and automations; one Postgres-backed queue (pg-boss 12 or BullMQ 6 Postgres backend) for high-throughput projector/integration sync; avoid Redis-only BullMQ unless throughput demands.
7. **Webhooks build vs buy.** Stack: own outbox + Inngest; integrations: Svix Cloud. Resolution: outbox is the source in both; Svix Cloud Basic for delivery/portal behind an interface.
8. **Migration router vs edge policy.** Migration: Cloudflare Worker in front of yayatoh.com; security/stack: never put Cloudflare in front of Vercel (BotID degradation, Origin Rules Enterprise-only). Resolution: Worker is acceptable only during Phase A because it fronts the Laravel VPS and fetches Vercel by absolute origin; accept degraded bot detection temporarily; remove the Cloudflare proxy at cutover and standardize on Vercel edge. If that is unacceptable, use Next.js `rewrites.fallback` with direct-to-R2 uploads.
9. **Tenant apex.** Multi-tenant report: dedicated `*.yayatoh.events`; current product uses `abc.yayatoh.com`. Resolution: new tenants on the dedicated apex; `abc.yayatoh.com` retained as a custom domain (or 301) to preserve links, the ABC app and marketing.
10. **Seat-hold TTL.** Site copy 8 min vs vendor 5 min (UNVERIFIED); seating: 10 min → 15 at payment; payments: 10 min + one extension; seats.io 15. Resolution: 10 min default, +5 min at payment start, tenant-configurable; verify legacy value during Phase 0.
11. **Locale count.** Vision and several reports say 12; audit lists 13 codes. Resolution: 13 locale codes (12 languages incl. two Chinese variants); size fonts, templates and Tolgee for 13.
12. **Scanner client baseline.** Offline report assumes the Yayatoh app is attendee-only and the scanner client is new; audit shows ABC app 1.2.3 "Update scan features" and web scanners. Resolution: treat scanner presence per app as UNVERIFIED; plan PWA + native Organizer app regardless; verify ABC app source in Phase 0.
13. **Auto-seating solver.** Wedding report: greedy/CSP + local search with weights hidden; seating: Lewis & Carroll tabu + CP-SAT. Resolution: tabu search in a Web Worker (P1), CP-SAT service later; weights in an advanced drawer.
14. **Prismm sunset dates** conflict (Cvent: cutoff 2026-08-26/editing to June 2027; third parties: view-only 2026-10-01/shutdown 2026-12-31). Resolution: plan the agency tier for Q1 2027 regardless; re-verify before marketing.
15. **Stripe hosted onboarding** — all agree on `requirement_collection=stripe`; no conflict, noted for completeness.
16. **Public seat picker rendering.** Security: SVG with accessible list; seating: Konva. Resolution: Konva for editor and large maps, SVG for small/static/print, accessible list mode on every surface.
17. **Postgres provider.** Stack: Neon; analytics/offline mention Supabase Realtime and Tiger Cloud options. Resolution: Neon; TimescaleDB and Supabase Realtime are out unless hosting changes.
